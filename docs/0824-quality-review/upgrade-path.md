# v0.9.44 → 0824 升级体验质量评审

评审对象:`origin/cursor/0824-cde6 @ 2d41ea8b`,对照 `v0.9.44`。只看升级路径:数据库迁移的执行安全、前端持久化状态的承接、i18n 缺键的升级回归、旧备份与旧口令的兼容。云同步协议本身的实现质量见 `cloud-sync.md`,交叉面见 `cross-cutting.md`,此处不重复。

## 结论

**升级执行层是这一轮做得最认真的部分,总体判断:比 v0.9.44 的任何一次版本跳跃都更安全,但不是无坑。**

正面判断的依据不是"有测试",而是测试的对准方式变了:0824 的升级夹具第一次把「上一发布版的精确 schema 元组」(vfs 20260808 / chat_v2 20260806 / mistakes 20260724 / llm_usage 20260525)写死进 fixture,升级预言(oracle)断言到字段级语义(NULL 保持 NULL、`_qa_flags`/`_occlusion` 字节不变)。迁移协调器对唯一一条越过通用回放冻结边界(V20260801)的新迁移显式收敛了两种中间态。旧口令路径为「v0.9.44 从不写加密标记」这个历史事实单独设计了升级分支,先试解既有密文再固化校验子。这些都是对着真实升级场景做的工程,不是模板化补测试。

但有三个会真实坑到用户的问题,按严重程度排列:

1. **换机/重装场景下,v0.9.44 时代的短加密口令(<8 字符)被新的最小长度校验锁死,旧加密备份无法通过任何产品内路径恢复。**
2. **`mistakes` 规范化迁移把 `source_type/source_id` 从 NULL 改写为空串,可能撞上去重唯一索引,导致升级在该库上失败;这个情形恰好没有被夹具覆盖。**
3. **加密标记升级(prove)要全量下载并全量解密最新备份,对多 GB 备份用户是一次无预期、无进度语义的大开销。**

以下分块展开。

## 一、数据库迁移:升级执行显著更安全

### 做对了什么

0824 相对 v0.9.44 只新增三条 SQL 迁移,全部是温和形态:`llm_usage` 加可空列(NULL=无测量,语义与既有 `cached_tokens` 一致)、`vfs` 的 `notes` 加可空 `props` 列(无回填)、`mistakes` 规范化历史 NULL/空串 JSON。没有表重建、没有数据搬移、没有需要长事务的回填。对升级用户意味着:首启迁移耗时基本可忽略,失败面被压到最小。

真正体现质量的是三件配套工程:

**其一,针对上一发布版的精确升级夹具。** v0.9.44 的 fixture 集只有四个通用历史形态;0824 新增 `release_v0_9_44_llm_usage` 和 `v0944_anki_library` 两个 fixture,`schema_tuple` 逐库锁定 v0.9.44 的准确版本号,oracle 断言"旧式不带新列的 INSERT 继续合法"、"未测量值保持 NULL 而不是被填 0"。这把「从上一个发布版升上来」从一个假设变成 CI 里可执行的事实,且 release 层的迁移门禁是 fail-closed(fixture 缺失不许出包)。

**其二,协调器对中间态的显式收敛。** `notes.props` 的 ALTER 超出了通用兼容回放的冻结边界,协调器为它写了专门的预修复:

```2355:2375:src-tauri/src/data_governance/migration/coordinator.rs
        let recorded = self.is_migration_recorded(conn, VERSION)?;
        let has_props = self.column_exists(conn, "notes", "props")?;
        match (recorded, has_props) {
            (true, false) => {
                tracing::warn!(
                    "🔧 [PreRepair] VFS: V{} 已记录但 notes.props 缺失，补齐列",
                    VERSION
                );
                self.add_column_if_missing(conn, "notes", "props", "TEXT")?;
            }
            (false, true) => {
                tracing::warn!(
                    "🔧 [PreRepair] VFS: notes.props 已存在但 V{} 未记录，补齐迁移记录",
                    VERSION
                );
                self.ensure_refinery_history_table(conn)?;
                self.mark_migration_complete(conn, runner, VERSION)?;
            }
            _ => {}
        }
```

「列已落盘但记账丢失」和「记账在但列缺失」这两种崩溃残留态都能自愈,且"两者都缺时不抢跑、交还 Refinery"的边界划得干净。配合 `apply_vfs_init_missing_tables` 对旧库缺表的补齐(并注意到了必须先于 change_log 修复执行、必须跳过已被 V20260214 删除的 `notes_versions`、重建的 notes 表要按记账状态决定是否带 `props`),升级路径对"半迁移库"的容忍度比 v0.9.44 高了一个档次。

**其三,降级不炸。** v0.9.44 的 Refinery runner 配置了 `set_abort_missing(false)`,回退安装 v0.9.44 时未来版本的迁移记录不会阻止启动,新增的可空列会被旧版代码无害忽略;`mistakes` 规范化本身幂等,降级后再升级也安全。升级是可逆的——这一点对"升级出问题想回退"的用户是实打断层的保障,虽然它是 v0.9.44 就有的性质,0824 的三条迁移全部保持了与它兼容的形态,没有引入单向门。

### 坑:规范化 × 去重唯一索引的未测冲突

`V20260824__normalize_anki_card_optional_json.sql` 的最后两条 UPDATE:

```23:31:src-tauri/migrations/mistakes/V20260824__normalize_anki_card_optional_json.sql
-- source_type/source_id are NOT NULL in the consolidated schema, but early
-- runtime-created tables and imported/synced rows may predate that constraint.
UPDATE anki_cards
SET source_type = ''
WHERE source_type IS NULL;

UPDATE anki_cards
SET source_id = ''
WHERE source_id IS NULL;
```

而 `anki_cards` 上存在以这两列开头的**部分唯一索引**(V20260724 重建版):`UNIQUE (source_type, source_id, CASE ... END) WHERE is_error_card = 0 AND deleted_at IS NULL`。SQLite 的唯一索引把含 NULL 的键视为互不相等,所以历史库里可以合法共存多行「source 为 NULL + 内容相同」的卡(迁移注释自己承认这类行来自早期 runtime 建表和导入/同步写入,而 `is_error_card` 默认 0,这些行会进索引)。规范化把它们统一改成 `('', '', 同内容)` 后,第二行 UPDATE 即报 `UNIQUE constraint failed`,整条迁移失败,`mistakes` 库升级中断。

概率不高——需要同一内容的卡片恰好有两行以上 NULL source——但触发者恰恰是「数据最老、最乱的重度用户」,即升级路径最该保护的人群。失败后果是 fail-closed(不丢数据,横幅报失败并可复制诊断),但用户被卡在升级上,自己无法解开。

更要紧的是夹具的覆盖缺口:`v0944_anki_library` 的 seed 里,那张"NULL JSON"卡的 `source_type/source_id` 写的是 `''` 而不是 NULL——迁移注释声称要处理的 NULL source 情形,夹具一行都没有,冲突对更无从谈起。这条迁移的 `dangers` 在 migration-lock 里登记为空数组,和它的实际风险面不匹配。

**建议**:UPDATE 前先对 `(source_type IS NULL 或 source_id IS NULL) 且落在索引谓词内` 的行按规范化后的键做一次去重(比如给 dedup 键即将碰撞的行保留最新一行、其余标记 `deleted_at`),或者至少改成 `UPDATE OR IGNORE` 加事后清点;同时给夹具补一对会碰撞的 NULL source 行。

### 值得记一笔的次要交互

规范化 UPDATE 会触发 `anki_cards` 的 `AFTER UPDATE` change_log 触发器,被修的行进入行级同步通道,把 `[]`/`{}` 回推到云端和其它设备。迁移没有碰 `updated_at`,所以在字段级合并里不会抢赢远端较新的写入,量级也只限异常行——行为大概率良性,但"升级即产生同步流量"这个耦合没有任何测试固定它,多设备混版本(一台 0824、一台 v0.9.44)下的传播语义是靠推理而不是靠断言保证的。

## 二、旧备份与旧口令:兼容主线守住了,但换机场景有硬伤

### 做对了什么

**容器格式零改动。** DSBK v1(整文件)/v2(分块)的字节布局、默认 Argon2id 参数(64 MiB/t=3/p=4)在两版之间完全一致,解密路径继续同时接受 v1/v2。v0.9.44 的本地加密备份和云端密文在 0824 全部可解——这是旧备份兼容的地基,守住了。

**KDF 参数上限的方向感正确。** 0824 给所有派生入口(校验子、v1/v2 解密、文件密钥会话)加了统一的应用级上限(1 GiB / t=16 / p=8),在分配任何内存之前 fail-closed,防的是云端不受信对象带异常参数把应用拖死。注释里明确写了"只许向上放宽,不许收紧——收紧会拒收自家旧备份",并有单测锁住 `DEFAULT_M_COST <= KDF_MAX_M_COST_KIB`。这是少见的、把"未来别人改这行会坑升级用户"提前写死的防御。

**为 v0.9.44 的"无标记"历史单独设计了升级分支。** v0.9.44 支持加密上传但从不写 `.encryption-marker`。0824 上传前遇到标记缺失时,不是直接用本机口令登记 v2 校验子(那会把一个敲错的口令固化成此后所有设备的基准),而是先下载最新旧备份、用本机口令完整试解,通过才登记;历史明文 ZIP 则允许直接开启 E2EE。v1 标记(中间版本产物)的一次性升级走同样的试解证明。错口令设备在写入任何备份对象之前就被拦截,并保持标记原样等待正确口令的设备来完成升级。整个状态机(缺失/损坏/v1/v2 缺校验子)每个分支都有明确的 fail-closed 归宿和可读的错误文案,这是旧口令兼容做得最扎实的地方。

**外围收尾也到位**:加密 ZIP 断点续传不把口令持久化进检查点,续传要求重输、缺失时在改动目标目录前失败;自动备份的 `recovery_kind` 改为按 ZIP 内实际清单判定,便携归档不再被误标成可整槽恢复的灾备点(v0.9.44 会误标,升级用户对旧备份能力的认知从此是诚实的);旧版 LegacyCandidate ZIP 的导入升级校验原样保留。

### 坑一(最重):8 字符下限锁死旧短口令的换机恢复

v0.9.44 对加密口令没有任何长度限制;0824 在前端和 `secure_store` 两层都加了 8 字符下限:

```2064:2068:src-tauri/src/secure_store.rs
        if cloud_encryption_password_too_short(update.encryption_password.as_deref()) {
            return Err(SecureStoreError::CloudEncryptionPasswordTooShort(
                cloud_encryption_password_too_short_message(),
            ));
        }
```

校验只作用于**显式提交的新口令**(前端 `isExplicitCloudEncryptionPasswordTooShort` 对空输入放行、后端对 `None` 放行),所以同机升级的存量短口令继续可用,这个边界划得对。但它漏了一个升级路径上必然出现的场景:**换新机或重装后恢复旧备份**。此时用户必须重新输入口令,而设置了 6 位口令的 v0.9.44 用户会被前端和后端双双拒绝——解密路径本身完全能解这份备份(容器格式没变、KDF 上限远高于默认参数),用户却连让口令进入解密流程的机会都没有。产品内没有任何豁免通道:云恢复的口令只从 secure_store 读,加密 ZIP 导入的口令入口同样经前端最小长度校验。

这不是理论坑:强制最小长度的动机(弱口令让加密形同虚设)恰恰说明存量用户里有人用着短口令。对他们来说,升级后一旦丢失设备,云端密文在自家产品里变成打不开的黑盒——只能翻出 v0.9.44 安装包先恢复再升级,而普通用户不会知道这条路。

**建议**:把最小长度校验定性为"新设口令的准入",在恢复/解密入口放行任意长度的既有口令(这不降低安全性,密文已经存在);或至少在拒绝文案里指出"若这是恢复旧备份的原口令"的处置路径。

### 坑二:标记升级的隐藏成本

`prove_password_against_existing_backups` 的证明方式是下载 manifest 最新版本的**完整备份对象**并**全量解密**到临时文件。对多 GB 备份的用户,升级后第一次加密上传前会先发生一次全量下载 + Argon2 派生 + 整包解密,UI 侧只表现为上传前长时间无进展。证明口令正确其实只需要头部 + 第一个分块(v2 每块有独立 AEAD tag,首块验证通过即证明密钥正确);v1 整文件格式才需要全量。当前实现为了复用既有解密管线选了最重的路径,可以理解,但成本没有向用户暴露,也没有降低它的打算(临时解密产物仅用于验证即弃)。

同时 prove 只试 manifest 的 latest 一个版本:该版本恰好损坏时,持有正确口令的用户也会被 fail-closed 拦下,错误文案虽然给了人工检查的指引,但产品可以做得更好(自动回退试次新版本)。

### 坑三:升级窗口内明文混布防线未闭合

「拒绝向曾加密的 root 上传明文」这道门依赖云端标记或本机记忆,而 v0.9.44 的 root 两者都没有。升级后到首次 0824 加密上传之间的窗口里,用户清掉口令改明文上传不会被拦。这不是回归(v0.9.44 本来就不拦),但意味着 0824 宣传的混布防护对存量用户不是升级即生效,而是"首次加密上传后才生效"——文档和评审口径里应当写清这个时间点。

## 三、前端持久化:防御式承接,质量好于机制

三处针对 v0.9.44 存量状态的处理都是对的:

- **Composer 输入区**:`normalizeRestoredComposerState` 把 v0.9.44 的持久化 payload 当外部边界对待——保留合法字段、按当前面板键集补默认、丢弃已退役的 rag/search/learn 键和畸形值,注释直接点名 v0.9.44,配有专门测试。升级后旧会话的输入框状态不会因为形状漂移炸 render。
- **阅读进度持久化**:从"dispose 时回读组件活 ref"改为创建时快照 + `readingProgress`/`bookmarks` 白名单。这修的是真 bug(node 切换时旧控制器把新 node 数据串写进旧路径;`highlights` 误入进度通道触发 OCC 冲突),对升级用户意味着 v0.9.44 时代攒下的阅读数据在 0824 被更窄、更不易误伤的通道写入。
- **Workbench 设置**:壁纸与平铺边距逐字段解析加 clamp,任意旧值/坏值回退默认,不会让一个越界数字弄坏整个工作台。

**保留意见**:这三处都是各自为政的无版本号 sanitize,仓库没有集中式的"持久化状态版本迁移"框架,也没有升级清理清单(v0.9.44 写下、0824 不再读的 localStorage 键会永久残留)。目前每个边界的质量靠作者自觉,这一轮的自觉度很高,但机制上没有东西保证下一轮还这样。作为优化空间记录,不构成本次扣分项。

云配置的 localStorage → 后端 SSOT 一次性迁移是 v0.9.44 已有机制,0824 原样保留并保持了"后端已确认清除时不许 stale 缓存复活配置"的语义。注意它和坑一有一个组合效应:从未在 v0.9.44 完成 SSOT 迁移的更老用户,首启 0824 时迁移会把 legacy 配置里的加密口令提交给 `update_cloud_credentials`,短口令会让整个 `resolveCloudStorageConfig` 抛错,云配置直接解析失败——这是坑一的又一个触发面。

## 四、i18n 缺键:审计式修复到位,守卫策略仍是清单式

### 做对了什么

`releaseUpgradeI18n.test.ts` 是这一块的核心产出,值得肯定的是它的修复取向:13 组升级审计发现的缺键,全部改为**复用两种语言都已存在的键**,而不是就地补一批只有单语言的新键;测试同时锁住"审计过的缺失键路径不得在代码里复活"。对中英复数形态的结构性差异(中文无 `_one/_other`)也做了显式处理——组件里带 `defaultValue` 兜底,测试分别断言英文的复数形态键和中文的单键存在。当前两个 locale 的键集合除英文复数形态外完全一致,新周期新增的所有命名空间(含 `migration.json` 的 style_lab 段)都保持了双语齐平。

配套地,0824 新增了 35+ 个 `*.i18n.test.ts`,把"这个组件引用的键必须在可解析 locale 里存在"下沉为模块级契约,覆盖 dstu、learning-hub、workbench 驱动、mobile 输入栏拆分等升级中大改的区域。相比 v0.9.44 时代缺键只能靠人肉审计发现,这是实质进步。

### 仍会坑用户的部分

**后端用户可见文案语言混杂,且没有收敛计划的迹象。** 同一批改动里,S3 不可用的稳定文案是中文("当前安装包不支持 S3 兼容存储,请改用 WebDAV。"),FTP 不可用是英文("FTP/FTPS storage is not available on Android."),E2EE 系列长文案全部是中文硬编码。前端的补救层(`localizeCloudError.ts` 按稳定错误码本地化、原文附括号)覆盖了主要设置页路径,方向正确;但任何未经过这层的展示面——日志、非设置页的 toast、`raw` 原文括号本身——都会把混语言文案直接推给用户。英文用户在升级后的新功能(恰恰是错误处理最密集的云备份区)里会成段看到中文。稳定 code 机制已经铺好了,缺的是把 message 的用户可见性收敛为"仅 code 进 UI,文案全部前端出"。

**守卫是清单式而非全量式。** `check-i18n.mjs`(能扫描代码引用键与 locale 的差集)在两版之间零改动、依旧没有接入 CI;CI 里跑的是 vitest 全量,它只能守住已经写进测试的键。也就是说,这一轮升级审计抓出来的 13 组缺键被永久锁死了,但下一轮新代码引入的缺键仍然要等下一次人工审计。以这个仓库的 i18n 测试密度,把"全部 `t()` 引用键必须双语存在"做成一条 CI 静态检查的边际成本很低,收益是把这类升级回归从"审计发现"变成"提交时拦截"。

## 五、优化空间汇总

按投入产出排序:

1. **修 `mistakes` 规范化与去重唯一索引的冲突**(迁移内先去重或 `UPDATE OR IGNORE` + 清点),并给 `v0944_anki_library` 夹具补真正的 NULL source 行与碰撞对。这是唯一可能让升级本身失败的点。
2. **给旧短口令开恢复通道**:最小长度只管新设口令,恢复/解密入口放行存量口令。这是唯一可能让用户数据变成打不开黑盒的点。
3. **prove 降本**:v2 容器只验首块即可证明口令;prove 失败时回退试次新版本。
4. **把 `check-i18n` 类全量键校验接入 CI**,把点状 i18n 契约升级为提交时守卫。
5. **后端用户可见错误文案去语言化**:稳定 code 已就位,把 message 从 UI 展示面撤下。
6. **给"迁移触发同步传播"补契约测试**(规范化行进 change_log 后的多设备混版本行为),或在同步侧对迁移产生的 change_log 记录做标记。
7. 长期项:持久化状态的集中版本迁移框架与升级清理清单,替代逐点防御式 sanitize。

## 总评

从 v0.9.44 升到 0824,用户拿到的升级过程比以往任何一次都更被认真对待:迁移是对着上一发布版的精确形态测的,崩溃残留态能自愈,降级可逆,旧密文可解,旧口令的历史包袱有专门的状态机承接,升级审计发现的 i18n 缺键被修复且防复活。这一轮的升级工程值得作为后续版本的基线。

扣分集中在两处"边缘但致命"的场景——最老最乱数据的唯一索引冲突、短口令用户的换机恢复——以及一处成本不透明(prove 全量解密)。三者共同点是:主路径测试都很密,但"存量用户里最不标准的那部分人"恰好落在测试覆盖之外。升级体验的质量上限,取决于对这部分人的想象力。
