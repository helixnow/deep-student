# Anki Connect / APKG 导入导出质量评审

对照范围为 `v0.9.44` 与 `2d41ea8b`，仅检查 `anki_connect_service.rs`、`apkg_exporter_service.rs`、`apkg_importer_service.rs`。这三个文件中，`anki_connect_service.rs` 没有差异；实际改动集中在 APKG 媒体导入报告、安全落盘及导出单文件限额。

结论：方向正确，但不宜把这版认定为“媒体完整导入/导出闭环”已经完成。结构化报告、符号链接防护、解压后限额和音视频回链明显优于基线；然而同名媒体的数据完整性、导出限额与自家导入限额的一致性仍有高风险缺口。建议修复前不要以无损往返作为对外承诺。

## 需要优先处理的问题

### 高：同名文件只凭文件名复用，可能链接错误内容，还会虚报导入成功

`extract_declared_media` 在发现目标普通文件已存在时，直接把它加入 `media_paths` 并增加 `imported_keys`，随后 `continue`；包内对应的数字条目是否存在、内容是否相同都不会检查（`apkg_importer_service.rs:706-719`）。

这会产生两个实际问题：

- 媒体目录已有 `image.png`，新 APKG 携带同名但不同内容的文件时，新包的卡片会静默链接旧文件，报告仍为成功。
- 清单声明了某数字条目但包内缺失时，只要媒体目录恰好有同名文件，也会绕过 `archive.by_name(key)` 的缺失检查，被计为成功。

本次改动还把旧版的 `media_paths.len()` 改成按清单键累计 `imported_keys`。新增测试明确让两个不同数字条目都映射到 `dup.png`，只落盘第一个条目的字节，却断言 `media_imported == 2`、`media_skipped == 0`（`apkg_importer_service.rs:3956-3978`）。这既掩盖内容冲突，也改变了旧字段“成功落盘的媒体文件数”的语义。

应先打开并校验每个包内条目，再按内容哈希决定复用。内容不同的同名文件应明确报冲突，或确定性重命名并同步改写卡片字段引用；至少不能把未读取、未落盘的条目计为成功。`media_imported` 应继续表示实际可用的唯一文件数，另设条目计数时使用新字段。

### 高：导出侧 256 MiB 上限既可绕过，也无法保证被本应用重新导入

导出侧只在收集阶段读取一次 `metadata.len()`（`apkg_exporter_service.rs:1142-1158`），真正写 ZIP 时仍使用无上限的 `std::io::copy`（`apkg_exporter_service.rs:1187-1190`）：

- `metadata()` 失败会落入 `_` 分支继续导出；
- 非普通文件以及检查后继续增长的文件没有流量上限，可能造成长时间阻塞或磁盘耗尽；
- 该限制只是“每文件 256 MiB”，没有限制媒体总量和最终 APKG 大小。

导入器却在入口拒绝大于 256 MiB 的整个 APKG（`apkg_importer_service.rs:237-241`、`269-273`）。因此一个接近 256 MiB 的媒体文件加上 collection/ZIP 开销，或两个较小媒体文件，就可能由本应用成功导出、再被本应用直接拒绝，所谓“与导入侧对齐”并不成立。

应只接受普通文件，将媒体先用 `MAX + 1` 的有界流复制到临时文件并确认大小，再写入最终 ZIP；同时按导入器的“压缩包总大小、总解压大小、单条目大小”三层预算做导出预检。最终产物也应在原子替换前验证总大小。

### 中：把带路径的清单名压平为 basename，但没有同步改写字段引用

`sanitize_media_filename` 会把 `nested/dir/photo.jpg`、`../escape.png` 甚至 `/etc/passwd` 接受并压平为 basename（`apkg_importer_service.rs:639-651`，测试在 `3570-3592`、`3759-3798`）。落盘映射仍以原始清单名为键，因此首次导入时 `images` 可以指向压平后的文件；但卡片字段中的 `src="nested/dir/photo.jpg"` 保持不变。

再次导出时，导出器只按 `images` 路径的 basename 打包为 `photo.jpg`，字段仍引用 `nested/dir/photo.jpg`，清单名与字段引用不再一致，媒体往返断裂。多个不同路径压平为同一 basename 时还会叠加同名冲突。

更稳妥的选择是拒绝任何不等于安全 basename 的清单名；若确实需要兼容路径名，则必须建立“原名 → 最终名”映射，统一改写所有 HTML/audio 引用并检测压平冲突。

### 中：媒体落盘不参与导入事务，失败导入会留下孤儿文件

媒体在 `parse_archive` 内先写入最终媒体目录（`apkg_importer_service.rs:544-577`），之后才解析 collection（`624-629`），再由 `persist_package` 写业务数据库（`293-294`、`2053` 起）。后两步任一失败，已经创建的媒体文件都不会回滚。重试时这些文件又会走“同名直接复用”分支，使失败残留进一步变成错误成功。

应先解到本次导入独占的临时目录；collection 校验和数据库事务成功后，再按已确定的冲突策略原子发布媒体。发布失败时需要可回滚清单，不能让数据库与文件系统各自提交。

## 做得较好的部分

- `mediaReport` 保留旧字段并对空报告省略序列化，原因码、全量计数和最多 20 个样本文件名兼顾了兼容性与可观测性。
- 对现代清单解析失败、清单缺项、孤儿数字条目、不安全文件名、目录不可用和 I/O 错误都给出了结构化原因，且排序后处理，结果稳定。
- `symlink_metadata`、拒绝非普通目标、`create_new` 以及失败后删除半成品，修复了基线中 `File::create` 可跟随悬空符号链接的安全问题。
- 现代媒体的 zstd 实际解压量受限，新增测试覆盖解压炸弹、图片与音频回链、JSON 契约及一次正常导入—导出—再导入路径，测试针对性较好。

## 收口建议

先统一“媒体条目数、唯一文件数、实际写入数”的术语和 API 语义，再把内容哈希冲突处理、临时目录提交、字段引用改写放进同一条导入流程。导出侧则应共享导入侧的限额配置，而不是复制一个同值常量。`media_dir` 文档声称返回绝对路径，但 `with_media_dir` 接受并原样返回相对路径，也应在入口规范化或修正文档。

`anki_connect_service.rs` 在本次对照中无改动，因此本轮不能把 AnkiConnect 的批量、重试或媒体同步能力算作此次改造收益，也没有针对其未变化实现追加复审结论。
