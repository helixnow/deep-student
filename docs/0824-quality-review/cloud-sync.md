# 云同步 / WebDAV / S3 / FTP / E2EE / ZIP 恢复质量评审

## 结论

我对这块改造的判断是：**相对 v0.9.44 有实质性提升，关键安全门大多是真接线，不是只补文案或测试；但还不能给无条件通过。**

`2d41ea8b` 已把云备份从“能传文件”提升成一套较完整的失败闭合链：大文件流式传输、上传后大小核验、下载后 SHA-256、每设备 manifest、列表截断拒绝、同步租约、E2EE marker 与密码校验子、旧密文试解、ZIP 密封载荷、恢复前完整性校验和 A/B 槽切换均在生产路径中。WebDAV、S3、FTP 的本轮修改也针对真实故障形态，不是协议点堆砌。

不过，当前仍有三类需要优先处理的系统性问题：

1. WebDAV/S3 的内存对象读取没有总字节上限，可被持续有进展的响应拖到 OOM；
2. 多处“PUT 后复读”只能发现坏写，不能从坏写中恢复，tombstone 和设备 manifest 都可能进入 fail-closed 死锁；
3. E2EE root 首次认领/旧 marker 升级没有远端 CAS 或租约，不同密码并发认领时仍可能产生同一 root 混用两套密钥的对象。

因此我的发布口径是：**有条件通过。单设备、正常后端、常规备份恢复场景的质量已经明显高于 v0.9.44；面向不可信云端、多设备并发和故障恢复的承诺仍应收窄。**

## 我看到的真实改造

### 1. 云备份主链不是表面重构

当前生产上传仍是全量 ZIP/DSBK 单对象，但主链已经做了几项关键修正：

- `sync_manager.rs:974-1002` 以流式 `put_file` 上传，先校验 provider 返回的 SHA-256 形态，再用远端 `stat` 核对对象大小；短写不能进入 manifest。
- `sync_manager.rs:1022-1060` 先发布新 manifest，再清理被裁剪对象；发布失败时新对象只是孤儿，发布成功后的 GC 失败也只是留下不可见孤儿，不会制造 manifest 引用已删除对象。
- manifest 从共享 read-modify-write 改成每设备文件，再在读取时合并（`sync_manager.rs:389-449`），避免不同设备直接覆盖版本列表。
- manifest 写入采用临时对象复读、最终对象复读两道门（`482-514`）；云端列表被后端截断时拒绝合并（`394-402`）。
- 下载按文件流式落盘并最终比对 manifest SHA-256；WebDAV 支持断点续传，其他不支持的后端明确整包重下，不冒充续传成功（`1092-1204`）。
- ZIP 上传、下载、删除与数据治理任务通过 `DataGovernanceOperationGuard` / `BACKUP_GLOBAL_LIMITER` 做进程内互斥；记录级同步另有云端 `sync_lease`，比 v0.9.44 的并发边界清楚很多。

这些改动的顺序基本正确：先验证，再发布引用，最后做可失败的 GC。相比只在成功路径上堆重试，这种设计更接近可恢复系统。

### 2. WebDAV / S3 / FTP 修改质量

这三块的价值在于修了具体实现错误：

- WebDAV 构造 URL 时先把 endpoint 已编码的 path segment 解码，再交给 URL API 编码一次（`webdav.rs:176-209`）；PROPFIND href 与 base path 也在同一解码空间比较。它确实修复中文、空格路径的双重编码。
- WebDAV 递归列举有目录数上限，并把触顶标成 `truncated`；同步层遇到截断会拒绝推进，而不是把不完整列表当删除事实。
- S3 `normalize_endpoint` 只对明确识别的 COS、OSS、S4、AWS bucket-host 形态剥离重复 bucket（`s3.rs:67-140`），没有对自建域名和 path-style 做激进猜测。这种保守边界是合理的。
- S3 multipart 有分块数/分块大小约束、分块重试、失败 abort，并会尽力清理同 key 的陈旧 multipart；列表完整处理 continuation token。
- FTP 把 not-found 收紧成“550/501 状态码 + 明确缺失语义”双门（`ftp.rs:239-313`）。权限拒绝和歧义 550 不再被吞成“不存在”；上传使用临时名再 rename，短流也有大小闸。

我不认为这些 provider 修复可以替代真实服务联调，但从源码看，它们都进入了实际请求路径，不是孤立 helper。

### 3. E2EE 是本轮最扎实的部分

v0.9.44 已支持 DSBK 加密容器，但没有 `.encryption-marker`。0824 补上的不是单一开关，而是一组相互配合的约束：

- marker 解析失败按“已存在”处理，避免损坏 marker 放行明文；写 marker 后逐字节复读（`sync_manager.rs:566-616`）。
- v2 marker 携带不可逆密码校验子。密码不一致、未知 KDF、v2 缺 verifier 均在写任何备份对象前失败（`638-735`）。
- 对 v0.9.44 遗留的“已有 DSBK、没有 marker”仓库，不再用首次输入的密码直接登记 verifier，而是先下载最新备份完整试解；失败不改 marker（`738-847`）。这补掉了“第一次输错密码反而固化错密码”的升级漏洞。
- 明文上传同时受云端 marker 和本机“该 root 曾加密”记忆约束；marker 被删也不能静默降级。
- 记录、文件和 blob 读取在本端启用 E2EE 时拒绝明文遗留对象，不只是整 ZIP 路径加密。
- Argon2 参数在派生前有应用级上限，DSBK v1/v2 共用检查；密钥材料使用 `zeroize`。这防止不可信云对象用恶意 KDF 参数制造资源耗尽。
- 大文件加解密采用分块容器和临时文件原子替换，不把多 GB 内容一次性放入内存。

从 v0.9.44 兼容角度看，默认 Argon2 参数和旧 DSBK v1 读取没有被破坏；本轮主要是在异常状态上收紧，方向正确。

### 4. ZIP 导入与整槽恢复真正改成 fail-closed

v0.9.44 在 `DataSpaceManager` 缺失时会回退写 `slotB`，写完后才因不能登记切槽而失败，可能留下无人管理的半恢复槽。当前实现把该门提前到磁盘预算、清槽和任何数据库写入之前（`commands_restore.rs:639-648`），这是重要的行为修复。

当前 ZIP/恢复链的有效防线包括：

- 在触碰目标目录前检查 ZIP 中央目录和密封载荷密码；
- `enclosed_name`、逐级 symlink/非目录检查、重复路径检查；
- 条目数、声明解压量、压缩比和实际写出量的双重预算；
- 临时文件提取后原子落盘，并核对实际大小；
- 解封后按原始 manifest 校验 SHA-256、拒绝未声明文件；
- partial/portable/coverage 不完整归档不能用于整槽恢复；
- 恢复前再做数据库 `PRAGMA integrity_check`、磁盘空间门和 A/B 管理器门；
- 任一数据库或资产恢复失败均不发布切槽状态。

加密全保真 ZIP 是 0824 新增能力；v0.9.44 的便携 ZIP 仍可导入检视，但不会被误判成可整槽恢复。安全边界最终由后端 manifest 校验裁决，不依赖前端弹窗。

## 主要缺陷与风险

### P1：WebDAV/S3 内存 GET 可无上限增长

`webdav.rs:1219-1254` 和 `s3.rs:797-832` 给每次读加了 90 秒停滞超时，也会在 EOF 后比对 `Content-Length`，但 `Vec` 本身没有总量上限：

- 对端只要持续发送小块数据，就可以无限延长总时长并持续扩容；
- 声明巨大 `Content-Length` 时不会在分配前拒绝；
- 声明很小但实际发送巨大内容时，也要等全部读入后才发现长度不一致；
- 无 `Content-Length` 时只有 EOF，没有任何大小闸。

这些 `get()` 正用于 manifest、变更分片、tombstone、marker、租约等控制对象，云端本来就在不可信边界内。这不是普通性能优化，而是可触发进程 OOM 的可用性漏洞。

建议在 trait 层定义控制对象硬上限：有声明长度时先拒绝超限；流式读取过程中按累计字节再次拒绝；无声明长度也使用 bounded buffer。若不同对象上限不同，应让调用方传预算，不能只设一个过大的全局值。

### P1：复读检测到了损坏，却没有恢复协议

PUT→GET 复读是正确的发布确认，但当前设计多处停在“发现错误”：

1. tombstone 兼容清单如果 PUT 实际留下损坏的短哈希对象，复读会报错，但坏对象保留。后续读取总是先命中该短哈希 key，解析失败后不会回退旧明文 key，也到不了 v4 不可变事件流。删除意图仍在本地队列和 v4 事件中，但同步可能永久 fail-closed，直到人工删除对象。
2. 每设备 manifest 最终对象写坏时，已验证临时对象会保留，但临时 key 以 `.tmp` 结尾，正常合并会忽略它；损坏的正式 `.json` 反而令整个 manifest 读取失败。临时副本目前是诊断残留，不是自动恢复点。

不能在复读不一致后简单 DELETE：不一致也可能来自并发赢家，删除会误删健康版本。需要的是有版本条件的恢复协议，例如 ETag/CAS、不可变版本对象加原子指针，或在持有远端租约时从已验证临时对象修复。至少应提供可识别、可审计的隔离与人工恢复入口。

### P1：E2EE marker 的首次认领仍有并发竞态

marker 的“先读状态、生成 verifier、覆盖 PUT、复读”没有条件写。两台设备可同时看到 Absent，分别用不同密码通过空仓检查，然后依次写入各自 marker；只要各自在被下一次覆盖前完成 GET，两边都可能认为认领成功并继续上传。

结果是：

- 最终 marker 只代表后写密码；
- 先写设备已经上传的对象和 per-device manifest 仍可见；
- 同一 root 出现两套互不兼容的密文，违背本轮试图建立的单密码不变量。

旧 v1 marker 升级也有同类问题。PUT 后复读证明“我刚才读到了自己的字节”，不证明之后不会被覆盖。应给 marker 认领/升级增加远端租约或 provider 条件写抽象；成功后还应在发布备份对象前再次确认 marker 的 verifier 未变化。

### P2：tombstone 兼容清单存在同设备 lost update

v4 不可变事件流本身设计较强：发布前取云端最大序号，事件 PUT 后复读，消费时校验 payload hash、路径、设备和序号断层，列表截断时拒绝推进水位。

问题在兼容清单。`data_governance_mark_blob_deleted` / `mark_asset_deleted` 是直接暴露的 Tauri 命令（`commands_sync.rs:3875-3934`），没有获取 `BACKUP_GLOBAL_LIMITER` 或远端同步租约。两个同设备调用可以同时读到 M，分别写 M+A、M+B，并在不同时间都成功复读，最终兼容清单只保留其中一份。

新客户端仍可从 v4 事件看到 A、B，因此这更像迁移/兼容风险，不是主删除流静默丢失；但当前“每设备清单不会丢项”的口径不能成立。应让直接 mark 命令至少进入同一设备的串行化通道，或停止对兼容清单做无条件 RMW 覆盖。

### P2：手动整包下载的 E2EE 防降级不对称

`cloud_sync_download` 下载后只看前四字节是否为 DSBK；非 DSBK 内容直接按明文 ZIP 保留，即使配置中有加密密码、云 root 也有 marker（`cloud_storage/mod.rs:503-557`）。

后续 ZIP 导入会拒绝明文包携带敏感目录，并把它限制为不可整槽恢复的 partial archive，所以这里暂未形成静默替换用户数据的漏洞。但用户会在“此 root 已加密”的情况下得到一个被当作普通下载成功的明文对象，错误边界和记录/文件下载不一致。建议下载前读取 marker；marker 存在却遇到非 DSBK 时直接报稳定的防降级错误。

## 半成品与能力边界

### backup-v2 / delta 目前是未接线积木

`delta_format`、`delta_upload`、`delta_restore`、`delta_gc`、`backup_lease` 已有大量格式、上传、恢复、GC 和租约实现，但模块注释明确写着没有 Tauri command、UI 或 `sync_manager` 生产接线。当前生产云备份仍是：

`完整 staging → 全量 ZIP → 可选 DSBK → backups/<version>.zip`

因此不能对外宣称已支持增量备份、内容去重、增量恢复或增量 GC。这里不是“差最后一个开关”，而是尚缺 E2EE marker 集成、迁移/兼容策略、端到端发布与恢复编排、UI 状态、失败恢复和真实后端验证。

这批代码的优点是边界写得诚实，还有源码锁防止误接；缺点是未接线实现已经形成较大的维护面。建议要么放到明确的 experimental feature 后并冻结对外承诺，要么以一次完整的端到端接线交付，而不是继续增加孤立原语。

### 平台与后端能力不能泛化

- Android 发行配置只承诺 WebDAV；FTP 在 Android 编译期排除，S3 取决于 feature。配置校验会按平台能力拒绝，行为是诚实的，但产品口径必须同步。
- FTP 不支持断点下载，失败后仍需整包重下；当前代码没有把它伪装成续传。
- WebDAV `%2F` 作为资源名字面字符的往返语义未覆盖；S3 未知供应商 bucket-host 不自动修正；这些属于兼容边界，不是本轮已证明能力。

## 次要质量问题

1. FTP `ensure_directory` 仍会对任意含 `550` 的 MKDIR 失败压低日志，且所有 MKDIR 错误都继续执行，最终靠后续 CWD/上传失败兜底。不会误报整体成功，但故障定位不够直接。
2. marker、manifest、tombstone 分别实现了相近的“序列化—PUT—GET—逐字节比较”逻辑，错误处理和恢复能力已经漂移。应抽象成带对象类型预算、版本条件和恢复策略的 verified publish primitive，而不只是复用一个无条件 PUT helper。
3. tombstone 的部分“源码守卫测试”只对源码字符串做 `contains`，即使生产调用被移除也可能继续通过。blob 有动态坏写用例，但 asset/workspace、GET 报错、坏对象后的下一轮恢复和双写交错仍缺动态覆盖。
4. 当前静态代码有很多安全注释和稳定错误码，这是优点；但注释里“不得报成功”容易被误读成“远端状态没有推进”。v4 事件先发布、兼容清单后发布，后者失败时前者可能已经可见。文档应明确这是安全的部分提交与幂等重试，不是事务。

## 建议的处置顺序

1. 给所有内存控制对象读取加硬字节预算，并补“持续小块”“超大 Content-Length”“无长度字段”三类回归。
2. 为 marker 认领/升级引入远端互斥或 CAS；覆盖首次双设备、不同密码和 v1 升级竞态。
3. 设计坏 manifest/tombstone 的可恢复发布模型，避免“检测成功、仓库永久卡死”；用故障注入证明下一轮可自动收敛。
4. 将直接 tombstone 命令纳入同设备串行化，并补双调用交错测试。
5. 统一整包下载与记录/文件下载的 marker 防降级政策。
6. 用真实 Nextcloud/坚果云、AWS/OSS/COS/MinIO、FTP/FTPS 做限流、断流、短写、列表截断和并发写矩阵；静态测试不能替代这一层。
7. 对 backup-v2 明确产品决策：完整接线或保持实验隔离，避免把代码存在性当成功能完成度。

## 最终评价

这次改造的核心价值不是“多支持了几个协议”，而是把多个原本会静默成功、半恢复或降级的路径改成了显式失败：上传短写不发布版本、列表不完整不推进、错密码不写对象、损坏 KDF 不计算、partial ZIP 不切槽、A/B 管理器缺失不先写数据。这些都是真正提升数据安全的变化。

但目前最薄弱的地方也很一致：**系统擅长发现异常，还不擅长在并发和坏写之后自动恢复。** 在补齐内存预算、marker 并发认领和损坏控制对象恢复之前，我会把 0824 定义为“主链质量达标、灾难与对抗边界未闭合”，而不是完整成熟的云同步方案。
