## PR #92 Feat/cloud storage ftp —— 详细审阅

整体评价：结构清晰，正确模仿了 WebDAV/S3 的既有模式（`StorageProvider` 枚举、`CloudStorage` trait、凭据单独存储、Debug 脱敏、前端 Tab UI、i18n 双语文案齐全），是一个有诚意的贡献。但存在 **1 个必须修复的阻断问题、若干高优先级问题**。

### 🔴 阻断（必须修复才能合并）

0. **【已实测证实】** 在 PR #92 分支 worktree 上实际运行 `cargo test --lib cloud_storage::`：**15 passed, 3 failed**。其中 `test_ftp_config_validation` 恰在预测的断言处失败（`config.rs:524: assertion failed: config.validate().is_err()`）——证实下述第 1 条。另外两个失败（`test_default_root`、`test_is_local_endpoint`）经比对测试体与实现，**与 main 完全一致，属上游 main 既有的失败测试**（`root()` 未做 trim、`is_local_endpoint` 不识别 `[::1]`），与本 PR 无关，但说明上游 CI 并未有效拦截该模块的单测失败，值得维护者注意。

1. **测试与实现矛盾，`cargo test` 必挂**。`config.rs` 中 `validate()` 对 FTP 分支注释写明「允许不安全的 FTP 使用（不强制 TLS）」直接返回 `Ok(())`，但新增测试 `test_ftp_config_validation` 断言「非 localhost 不使用 TLS 应该被拒绝」（`use_tls=false` + 远程 host → `is_err()`）。实现没有调用 `is_local_ftp_host`，该断言必然失败。作者只勾选了 `cargo build`，显然没跑 `cargo test`。需要作者二选一：
   - 方案 A：实现「远程 host 强制 TLS、localhost 允许明文」（与测试和 i18n 文案一致，更安全）；
   - 方案 B：保留宽松策略，删掉矛盾的测试断言并改 i18n 文案。
   注：`is_local_ftp_host` 在 `config.rs` 和 `ftp.rs` 各定义一份且**均未被生产代码使用**（死代码），i18n 文案「仅 localhost 允许明文」与实际行为也不符。三处互相矛盾。

2. **`tauri.conf.json` 的 android `versionCode` 从 13896 改成 13355 —— 版本号倒退**，明显是本地环境误提交，必须回退。

### 🟠 高优先级

3. **依赖选型欠佳：suppaftp v6 只有 async-std 后端**。该 PR 因此引入了整个 `async-std` 运行时（与项目既有 tokio 并存双运行时）+ `async-native-tls` → `openssl`/`openssl-sys`（Linux 构建需要 openssl 开发库，且加重所有平台编译负担）。suppaftp **v7+ 已支持 `tokio` 后端和 `tokio-async-rustls-ring`**，可与项目现有 tokio/rustls 栈无缝集成，建议升级并去掉 async-std/openssl。代码中也确实混用了两个运行时（`tokio::fs`/`tokio::time::sleep` + `async_std::io`）。

4. **`Cargo.lock` 含大量与 FTP 无关的改动**：`windows-sys` 0.60→0.61、`rustix` 的 windows-sys 0.52→0.59、`deep-student` 0.9.39→0.9.40 等，疑似顺手跑了 `cargo update`。应只保留新增依赖的最小 lock 变更，否则合并冲突风险高。

5. **全量读入内存**：`put_file` 用 `tokio::fs::read` 整文件读入内存上传，`get_file` 把整个远程文件下载进 `Vec<u8>` 再写盘。备份文件可能数百 MB～GB 级，会造成内存峰值。WebDAV 实现是否流式需对照确认，建议至少 `get_file` 改为流式落盘。

6. **LIST 解析脆弱**：手工按空白切分 Unix 风格 `ls -l` 输出（`parts[4]` 当 size、`parts[8..]` 拼文件名）。Windows/IIS FTP 返回 DOS 风格列表会解析失败；文件名含连续空格会被 `split_whitespace+join(" ")` 破坏。suppaftp 自带 `list::File` 解析器，应直接使用。另外对每个文件单独发 `MDTM`，N+1 次往返，目录一大就很慢。

### 🟡 中/低优先级

7. **读操作有写副作用**：`get`/`stat`/`list`/`check_connection` 都会先 `ensure_directory`（逐级 MKDIR）。「测试连接」按钮会在服务器上创建目录，`list` 一个不存在的 prefix 也会把目录建出来，语义令人意外。
8. **每个操作新建一次 FTP 连接**（connect→login→op→quit），同步大量小文件时开销巨大；后续可考虑连接复用。
9. **嵌套重试**：`get_file` 内部调用 `self.stat()`，两层都包了 `with_retry`，最坏 3×3=9 次连接尝试；且认证失败（密码错误）也会重试 3 次，可能触发服务器封锁。建议认证错误不重试。
10. `root` 为空字符串时路径拼接会出现 `//`（`format!("{}/{}", "", parent)`），多数服务器容忍但属边界隐患；`remote_path`/`join_paths` 只被测试使用，生产路径全部用手写 `format!`，建议统一。
11. `AppError::authentication` 实际映射到 `AppErrorType::Network`，类型语义不符（项目若无 Auth 错误类型可接受，但值得注明）。
12. `.gitignore` 加 `.trae/*` 属于个人编辑器目录，建议放进个人全局 gitignore（小事，可放行）。
13. 前端 `parseInt(port) || 21`：输入 0 或清空会静默变回 21，小瑕疵。
14. TLS 用默认 `TlsConnector::new()`（校验证书，安全性 OK），但自建 FTPS 多为自签证书，会直接失败——与作者「FTPS 未实测」的说明相符，可作为后续增强（需带警示开关）。

### 优点（值得肯定）

- 凭据处理正确：`Debug` 脱敏 + 密码走独立 credentials 通道 + 前端加载时清空密码字段，与 WebDAV/S3 模式一致。
- 前端 `dataGovernance.ts` 顺手消除了类型重复定义（统一从 `cloudStorageApi` 导入），是合理的清理。
- `isConfigValid` 把原来 `else` 兜底改成 `else if (provider === 's3')`，修正了分支结构。
- 下载落盘用临时文件 + 原子 rename，校验 SHA256，姿势正确。
- 测试覆盖了配置校验、Debug 脱敏、路径拼接（虽然有矛盾断言）。

### 🔴 补充发现：FTP 凭据持久化链路三处断裂（深入核查后确认，比上述问题更严重）

对照 `secure_store.rs`、`cloudStorageApi.ts`、`CloudStorageSection.tsx` 三端核实：

- **断点 1 —— FTP 密码明文写入 localStorage**：`CloudStorageSection.saveConfig` 构造 `safeConfig` 时只清空了 `webdav.password` 和 `s3.secretAccessKey`，**漏掉 `ftp.password`**，于是 FTP 密码随配置明文存入 `localStorage['cloud_storage_config_v2']`——这正是上游对其他两种凭据特意避免的。
- **断点 2 —— 后端安全存储根本不认识 ftpPassword**：`secure_store.rs` 的 `CloudStorageCredentials` 结构体只有 `webdav_password`/`s3_secret_access_key`/`encryption_password` 三个字段，**PR 未修改此文件**。前端 `saveCredentials({ftpPassword})` 发过去后被 serde 静默丢弃；`getCredentials()` 永远不会返回 ftpPassword → 设置页重启后密码框恒为空。
- **断点 3 —— 凭据合并函数没有 ftp 分支**：`loadStoredCloudStorageConfigWithCredentials()`（被 `SyncSettingsSection`、`useConflictResolution`、`DataGovernanceDashboard` 等自动同步路径使用）只处理 webdav/s3，provider 为 ftp 时落入 s3 兜底分支，不会从安全存储合并 FTP 密码。
- 综合效果：**自动同步路径目前「能用」完全是因为断点 1 把密码明文留在了 localStorage**；一旦按规范修复断点 1，FTP 同步立即全断。作者「仅 Windows 内网测试通过」大概率从未覆盖「重启后从设置页重连/自动同步」场景。修复需要三处联动：后端结构体加 `ftp_password` 字段 + 合并函数加 ftp 分支 + safeConfig 清空 `ftp.password`。

### 结论建议

**Request Changes**。必须修：#1（测试矛盾，二选一策略）、#2（versionCode 回退）、**凭据链路三处断裂（安全 + 功能双重缺陷）**；强烈建议修：#3（升级 suppaftp v7+/tokio/rustls）、#4（Cargo.lock 最小化）、#5（流式传输）、#6（用自带 LIST 解析器）。作者表态愿意持续维护此功能，建议给出明确修改清单引导。

### 维护者主动接管 PR 的操作指南（merge-and-improve 工作流）

贡献者一时改不完时，维护者有四种接管方式，按推荐顺序：

**方式 A：直接推提交到贡献者分支（最轻量，适合 #92/#99）**
- 前提：PR 页面勾选了 "Allow edits by maintainers"（fork PR 默认勾选）。

- 效果：修复提交直接出现在原 PR 里，贡献者署名保留、CLA 流程不变、review 历史连续。贡献者还能继续在自己分支上跟进。
- 注意：#99 的 head 是对方 fork 的 `main`（默认分支），往别人 main 推东西不礼貌且 GitHub 对默认分支的 maintainer-edit 有限制，#99 建议改用方式 B。

**方式 B：本地接管、开替代 PR（适合 #99 及需要重组提交的场景）**
