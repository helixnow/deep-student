## Channel 评估结论（不实施）

**结论：暂不引入 Tauri `ipc::Channel` 替代 `apply_ops` 单请求批量。**

| 维度 | 评估 |
|---|---|
| 现状 | ops 随一次 `acr:bridge-request` 整批到达；演出节奏由前端 pacing 本地控制；progress 已 ≤5Hz 独立事件 |
| Channel 收益 | 仅当单次 payload 极大（数千 op / 超大 note 文本）导致 IPC 序列化卡顿或超时预算吃紧时，流式分片才有意义 |
| 当前瓶颈 | 主成本在前端 DOM/RF 渲染与打字机 rAF，不在 IPC 吞吐；DESIGN §0.4 已明确「批量委托 + 前端本地节奏」 |
| 风险 | Channel 会拆散「一次回执 / 一次租约」语义，需重做取消、超时、partial 边界；与 mcp-bridge 模式分叉 |
| 触发条件（R3 再议） | DevPanel 实测单次 `apply_ops` 载荷持续 >8KB 且桥等待占主导；或 5k 节点批 op 序列化 p95 >50ms |
