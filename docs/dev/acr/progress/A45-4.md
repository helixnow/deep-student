## 设计决策与偏差

1. **reorderDock 参数形态裁决：`{ typeId, toIndex }`**。相比 `order: string[]` 全量数组：LLM 只需给一个 id 和一个整数，不必先精确复述整个数组（漏项/错序即失败）；范围校验简单可给出确定 hint；与 DockPinnedStore 的 `reorderDockPinned(from, to)` 语义一一对应；且单步移动天然自可逆（inverse 为回移）。
2. **快照 undo 的落地方式**：agentRuntime 的 undo 回放要求 inverse 动作必须是 manifest 已声明能力且过 inputSchema 校验，无法直接调 `setDockPinned(快照)`。因此对齐 tileWindows 手法——快照 + 用已声明能力组合精确恢复：pinApp 逆 = unpinApp（pin 恒追加末尾）；unpinApp 逆 = pinApp（重追加）+（非末位时）reorderDock 归位；reorderDock 逆 = reorderDock 回原位。每步 expect 都断言 `state_equals dockPinned=对应快照`，整体等价于快照恢复。
3. **可钉性判定**：`appRegistry.get(typeId)` 存在且 `showInLauncher !== false`。UI 的 Dock 右键菜单对「运行中」应用更宽松（可钉 launcher 隐藏的内容应用），agent 侧收敛到可发现集合，避免钉出无 resourceId 无法启动的死图标；此收敛写在能力描述与 hint 中。
4. **launcher 隐藏的既有固定项**：unpinApp 允许移除（如实 changed），但因 pinApp 不能恢复它，诚实**不注册 undo** 并在 message 说明——不假装可逆。
5. **允许清空固定区**：UI `toggleDockPinned` 无最小钉数限制，agent 对齐；但 WorkbenchDesktop 快照恢复时空 dockPinned 会回退 `DEFAULT_DOCK_PINNED`，该兜底行为写进回执 message（纪律：降级不静默）。
6. **i18n**：desktop manifest 的 undo label 既有惯例为硬编码中文（'恢复窗口焦点'/'恢复平铺前的窗口布局' 等），本任务跟随（「恢复 Dock 固定区」），未动 workbench.json。与 A45-1 templates 走 i18n 的做法不同属两文件各自惯例，留给协调者统一裁决。
7. **风险分级**：pinApp/reorderDock = low（改持久化视图态、可逆、幂等），unpinApp = medium（移除用户显式配置）。
