## 0. 结论（TL;DR）

1. **现状**：应用没有「更换备份密码」功能。换密码在今天等价于「换一个云端目录 + 全量重新上传」——上传前置校验会拒绝新密码写入旧目录（这是刻意的保护，不是 bug），错误文案已明确引导用户「核对密码或改用新的云端目录」。本文把这条路走通、写成用户可照做的流程（§2）。
2. **对照 Standard Notes**：SN 的产品行为是「原地轮换」——用户改密码后数据留在原处、后台按新密钥重新加密，两台设备在过渡期都能继续用。我们与它的差距是协议能力差距，不是安全性差距；把现状诚实告知用户比仓促实现半套轮换更重要（§3）。给出标记 v3 / 双校验子过渡窗 / 中断恢复的协议草案供下一轮评审（§4）。
3. **文件名元数据**：`backups/<时间戳毫秒>-<设备短ID>-<随机串>.zip`、`manifests/<完整设备ID>.json`、标记内 `created_by_device` 都是明文元数据。泄露的是**行为元数据**（设备数量、活跃时间规律、备份频率），不泄内容。收敛方案完全向后兼容：对外文件名改为纯随机中性 ID，时间/设备信息只留在 manifest 内（§5）。
4. **校验子健壮性**：现有实现对未知 KDF / 损坏字段已 fail-closed（有测试钉死）。**缺口确认**：对云端对象携带的 KDF 派生参数没有任何上限钳制——R10-verifier 计划交付的「Argon2 参数钳制」**未合入**，`derive_key` 与校验路径均原样使用云端数值，异常过大的参数会让应用在校验/解密时长时间无响应甚至内存耗尽。产品要求与验收标准见 §6，不描述构造方法。
5. 下一轮四个可认领实现任务（每条含可验证交付物与验收标准）见 §7。

**「换密码 = 换目录 + 全量重传」的完整推导**：用户在云存储配置里改掉 `encryption_password` 后，下一次上传走到校验子比对即失败（新密码 ≠ 标记登记的旧密码）；应用没有「用旧密码自证后改写标记」的入口，也没有重加密既有对象的机制。因此唯一可用路径是换一个云端根目录（新目录无标记，首次上传即以新密码登记 v2 标记），旧目录的历史版本仍只能用旧密码解密。记录级同步同理：新目录从零开始，旧目录的变更流不迁移。

## 2. 面向用户的「更换备份密码」流程（基于现状，今天就能照做）

> 目标读者：普通用户。本节应回写进用户指南 16（见 §7 任务 T4），此处为母本。

### 2.1 换密码前，请先想清楚三件事

1. **旧备份不会跟着换密码。** 旧云端目录里的历史备份永远只能用**旧密码**解开。换密码 ≠ 旧备份失效，而是新旧两套各自独立。请把旧密码记录在密码管理器里，直到确认不再需要旧备份。
2. **换密码需要一次全量重新上传。** 新目录是空的，第一次备份是整包上传（记录级同步也从零开始），流量和耗时与首次配置云端时相同。请在 Wi-Fi / 不限量网络下进行。
3. **所有设备都要换。** 每台配置了同一云端的设备都需要更新云端目录路径和新密码，漏掉的设备会持续报「密码不一致」或连不上（见 2.3）。

### 2.2 标准流程（单设备或逐台操作）

1. **先做一次本地备份**（数据治理 → 备份 → 导出）。这是换密码过程中的安全网，与云端无关。
2. 在云存储配置里，把**远程路径/目录**改为一个新目录（例如把 `…/deep-student` 改为 `…/deep-student-2026`；也可以在网盘里新建目录）。不要删除旧目录。
3. 把**加密密码**改为新密码，保存配置。
4. 点「立即备份到云端」。首次上传会在新目录登记新的加密标记，之后照常按版本保留。
5. 验证：在「云端版本」列表能看到刚上传的版本；有条件时在另一台设备（或本机）做一次「从云端恢复最新版本」演练。
6. **验证通过之前不要删除旧目录。** 建议保留旧目录至少到新目录攒下 2–3 个正常版本之后；删除旧目录是在网盘侧手工操作，应用不会代删。

### 2.3 过渡期：两台设备如何共存

设备 A 已换新目录+新密码，设备 B 还是旧配置。这是安全的中间态，不会损坏任何数据：

| 设备 | 行为 | 结果 |
|---|---|---|
| A（已换） | 向**新目录**上传/恢复 | 正常 |
| B（未换） | 向**旧目录**上传/恢复 | 仍正常——旧目录标记登记的是旧密码，B 的旧密码通过校验 |
| B（只改了密码没改目录） | 向旧目录上传 | 上传前被拒绝：「加密密码与该云端目录既有加密备份使用的密码不一致」，**云端不会写入任何对象**。把目录一并换掉即可 |
| B（只改了目录没改密码） | 向新目录上传 | 同样上传前被拒绝（新目录标记登记的是新密码）。把密码一并换掉即可 |

注意事项（要写进用户指南）：

- 过渡期 A、B 各自向不同目录备份，**两边的数据不会互相合并**。在 B 完成切换前产生的数据，靠 B 切换后的首次上传/同步带到新目录。
- 记录级双向同步在过渡期同理：B 切换前的变更只在旧目录的变更流里；B 切换后首次同步会把本机全部有效状态按新密码进入新目录，不丢数据，但旧目录变更流不迁移。
- 尽量缩短过渡期（当天完成所有设备切换），减少「两边各自演化」的心智负担。

### 2.4 中断后如何继续

- **整包上传中断**（断网/关机）：新目录里不会出现「半个可见版本」——版本先传对象、后发布 manifest（`sync_manager.rs:734-747`），中断时未发布的对象不会出现在版本列表。重新点「立即备份到云端」即可，无需清理。
- **下载/恢复演练中断**：WebDAV 与桌面 S3 支持断点续传（`.zip.part` 断点保留，R09-restore-ops），重试即从断点继续；FTP 仍为整文件重下（诚实无断点）。Android 只有 WebDAV。中断不影响云端。
- **换到一半忘了换到哪**：看两个信号——云存储配置里的远程路径是新是旧；「云端版本」列表最新版本的时间。旧目录始终完好，最坏情况就是从 2.2 第 2 步重来。
- **新密码忘了**：新目录的备份无法解密（密码不保存、不上传，无法找回）。此时旧目录 + 旧密码就是救命稻草——这正是 2.2 第 6 步要求保留旧目录的原因。

## 3. 与 Standard Notes 的产品行为对照

只对照**用户可感知的产品行为**，不展开其协议内部细节：

| 维度 | Standard Notes | 我们（现状） |
|---|---|---|
| 用户改密码后数据在哪 | 原地不动，服务端/同步目录不变 | 必须换云端目录，旧目录变成只读历史 |
| 重新加密谁来做 | 客户端在后台自动把条目按新密钥重新加密上传，用户无感 | 没有重加密机制；靠一次全量重新上传（用户显式操作） |
| 过渡期多设备 | 其他设备下次登录/同步时用新密码验证后继续用，数据无缝 | 其他设备必须手工改目录+密码；改错组合会被上传前拦截（不损坏数据，但有操作成本） |
| 旧密码的余生 | 轮换完成后旧密码彻底失效 | 旧密码继续守护旧目录历史备份，用户需自行保管到不再需要 |
| 中断恢复 | 协议带版本状态，客户端可续 | 靠「版本先对象后 manifest」的发布顺序保证无半成品，重跑即可 |
| 忘记新密码 | 数据不可恢复（E2EE 共同宿命） | 同左；但旧目录+旧密码天然是一份逃生备份（现状的意外优点） |

诚实评估：SN 的原地轮换建立在「自家服务端 + 单一 item 数据模型」上；我们是任意 dumb storage（WebDAV/S3/FTP）+ 整包 ZIP + 记录级变更流三种对象形态，原地轮换的工程量和风险都高一档。**短期最优解是把 §2 流程产品化（引导式换密码向导），中期再评估 §4 草案。**

## 4. 原地轮换协议草案（标记 v3 / 双校验子过渡窗 / 中断恢复）

> 性质：供下一轮评审的草案，**本轮不实现**。只描述协议状态与运维语义，不含实现细节。

### 4.1 目标与非目标

- 目标：用户在同一云端目录内更换密码；过渡期新旧密码并行可用；任意时刻中断可恢复；全程不出现「某对象谁都解不开」的状态。
- 非目标：不追求 SN 式无感后台轮换（首版允许用户显式触发并看进度条）；不迁移旧目录方案的历史；不做多密钥长期并存（过渡窗结束即回到单密码）。

### 4.2 标记 v3 结构（草案）

在现有 v2（单 `key_verifier`）之上，v3 允许**至多两个**校验子并存，并携带轮换状态：

- `active_verifier`：当前主密码校验子（轮换完成后唯一保留）。
- `retiring_verifier`（可选）：仅在轮换进行中存在的旧密码校验子。
- `rotation`（可选）：`{ started_at, started_by_device, state }`，`state ∈ { reencrypting, verifying }`。
- 兼容规则：v2 读者遇到 v3 标记必须 fail-closed（现有「未知版本/缺校验子按损坏处理」的行为已保证旧客户端不会误写）；v3 读者遇到 v1/v2 按现行为处理。

### 4.3 过渡窗规则（谁能读、谁能写）

| 阶段 | 上传（写） | 下载（读） |
|---|---|---|
| 无轮换（只有 `active`） | 密码必须匹配 `active` | 按对象头部参数解密，密码错即明确报错（现状） |
| 轮换中（`active`=新, `retiring`=旧） | **只允许新密码**写入新对象；旧密码设备被拒时错误文案明确提示「该目录正在更换密码，请在本机更新为新密码」 | 新旧对象各自用对应密码可解；恢复流程按对象逐个尝试用户提供的密码，解不开的对象提示「此版本由旧密码加密」 |
| 轮换完成 | 只认新密码（回到单校验子） | 全部对象已为新密码密文 |

### 4.4 轮换执行与中断恢复（运维语义）

1. 发起设备用旧密码自证（比对 `retiring` 前身 `active`）后写入 v3 标记，进入 `reencrypting`。
2. 逐对象「下载→重加密→以临时名上传→校验读回→原子改名/覆盖→登记进度」。每个对象的重加密是幂等的：DSBK 头部自带 salt/参数，重跑时凡是已能用新密码解开的对象直接跳过。
3. 全部对象完成后进入 `verifying`：随机抽样重解校验，通过后把标记收敛回单 `active_verifier`（v3 无 `retiring`），轮换结束。
4. **中断恢复**：任意步骤中断后，任何持新密码的设备都能从标记里读到 `reencrypting` 状态与进度，继续第 2 步；因为第 2 步幂等，重复执行安全。过渡窗内旧对象始终保持旧密码可解，**任何时刻用户手里至少有一把能解开每个对象的钥匙**。
5. **僵尸轮换回收**：`started_at` 超过阈值（如 7 天）且无进度推进时，UI 提示用户「上次密码更换未完成」，提供「继续」或「放弃（回滚标记到旧密码为 active）」两个出口；放弃只在尚无新密码对象、或新密码对象可全部安全删除时允许。

### 4.5 主要风险（进入下一轮评审清单）

- 双校验子使标记成为更关键的单点：损坏语义必须与现有 fail-closed 行为逐条对齐。
- 记录级变更流对象数量大（万级），逐对象重加密的时长与流量需要基准数据（可复用 R11-delta 的测量脚本）。
- FTP 无原子改名保证，轮换期间的覆盖写需要 provider 契约测试先行（`sync_provider_contract_tests.rs` 扩展）。
- 与 R11-lease（sync target 租约）天然耦合：轮换应持有租约，禁止并发同步窗口。

## 5. 备份文件名元数据：隐私评估与收敛方案

### 5.1 现状盘点（谁能看到什么）

对**云存储提供商、目录被共享/被列出的任何一方**（无需任何密码）可见：

| 明文元数据 | 载体 | 内容 |
|---|---|---|
| 备份精确时间（UTC 到毫秒） | `backups/*.zip` 文件名 | `20260824-063000-123-…` |
| 设备短 ID（6 位） | 同上 | 同一设备的所有备份可被串联 |
| 完整设备 ID | `manifests/<device_id>.json` 文件名、manifest 内 `deviceId` 字段、`.encryption-marker` 的 `createdByDevice` | 设备数量、每台设备的备份历史 |
| 应用版本 | manifest 内 `appVersion` | 用户所用版本（可推断未升级状态） |
| 备份大小与频率 | 对象大小、版本列表 | 数据量增长曲线、使用强度 |
| 记录级活动 | `data_governance/changes/<device_id>/…` 对象名与数量 | 每台设备的同步活跃时段 |

### 5.2 对普通用户的影响评估

- **不泄露内容**：启用 E2EE 后所有正文均为 DSBK 密文，文件名元数据不降低内容保密性。
- **泄露行为画像**：备份时间戳精确到毫秒 + 记录级变更对象的时间分布，足以刻画用户的作息/学习时段规律；设备 ID 串联可知设备数量与换机事件。对把备份放在**自有** WebDAV/NAS 的用户影响很小；对使用**第三方网盘**或**共享目录**的用户，这是无必要的暴露。
- **定级**：P2（隐私打磨项，非安全漏洞）。device_id 本身是本机生成的随机标识（恢复后还会轮换），不直接关联真实身份；主要问题是「本可以不给的信息默认给了」。
- **对照**：restic/rclone crypt 档的做法是对外一律不透语义文件名，元数据进加密清单——这是我们收敛的方向。

### 5.3 收敛方案（向后兼容，分两阶段）

**可行性根据**（§1 已核）：下载、恢复、裁剪、删除全部经 manifest 按 `id` 查找，没有任何代码从文件名反解时间或设备；`validate_version_id` 只要求 ASCII 字母数字 + `-`/`_`；manifest 排序用的是 `timestamp` 字段而非文件名（`merge_manifest`，`sync_manager.rs:202-215`）。

**阶段一（低风险，纯改名收敛）**：

1. 新版本对象名改为**纯随机中性 ID**（如 22 位随机字母数字），不含时间、不含设备短 ID。时间与设备信息仅保留在 manifest 的 `timestamp`/`deviceId` 字段（功能不减：版本列表 UI 显示的本来就是 manifest 字段）。
2. 设备 manifest 文件名由 `manifests/<device_id>.json` 改为 `manifests/<device_id 的短哈希>.json`，完整 device_id 只在 manifest 内容中保留。读取侧本来就遍历 `manifests/` 下全部 `.json`（`get_manifest`，`:290-310`），文件名不参与语义，兼容无虞。
3. 兼容性矩阵：旧客户端读新对象——中性 ID 通过 `validate_version_id`，按 manifest 下载正常；新客户端读旧对象——旧名照常在 manifest 里，无迁移、无孤儿。旧名对象随 10 版保留策略自然淘汰，无需主动改名。
4. `.encryption-marker` 的 `createdByDevice` 改为登记短哈希（新写入生效，旧标记不动）。

**阶段二（可选，随 §4 轮换协议一并评审）**：manifest 与标记本身按备份密码加密（restic 档）。代价是「无密码时连版本列表都看不到」，会改变现有「先看到版本、恢复时才要密码」的产品行为，需要单独的 UX 决策，不与阶段一捆绑。

## 6. 密码校验子健壮性复审（产品语言）

### 6.1 已达标并有测试钉死的部分

`crypto/backup_crypto.rs` 测试段（`:792-849`）已覆盖：

- 正确密码通过、错误密码判不一致（`password_verifier_roundtrip_and_wrong_password`）；
- 摘要与加密密钥域分隔、不可互推（`password_verifier_digest_does_not_leak_key`）;
- 未知 KDF 返回 `Err` 而非误判（`password_verifier_unknown_kdf_fails_closed`）；
- salt 非 hex、摘要长度非法返回 `Err`，摘要内容被改判「不一致」（`password_verifier_corrupted_fields_fail_closed`）。

调用方 fail-closed 语义在 `sync_manager.rs` 测试段亦有集成钉死（错密码上传前失败且不写任何对象，`:1600-1624` 一带）。

### 6.2 缺口：派生参数无上限（R10-verifier「Argon2 参数钳制」独立复审结论）

**复审结论：未交付，缺口仍开。** ROUND-10 计划由 R10-verifier 交付参数钳制，FIX-QUEUE 中 R09-restore-ops 也把它列为「R10 需补」项；但基线 `f96a09a9` 上：

- `check_password_verifier`（`backup_crypto.rs:688-694`）把云端校验子里的 `m_cost/t_cost/p_cost` 原样传入 `derive_key`；
- DSBK 解密路径（`decrypt_backup_with_key_provider`，`:127-134`；流式 `decrypt_backup_file` 同理）把文件头里的参数原样传入 `derive_key`；
- `derive_key`（`:26-44`）只做 Argon2 库自身的合法性检查，**没有应用级上限**。

产品后果（不涉及如何构造，只陈述行为要求的动机）：Argon2 的内存参数就是「校验这一次要吃多少内存」。云端目录是用户自有的外部存储，其中对象可能被损坏、被第三方工具改写或来自未来版本；一旦读到**异常巨大的派生参数**，应用会在「校验密码」或「解密备份」这一步长时间无响应、甚至因内存耗尽被系统杀死——用户视角是「点了上传/恢复就卡死」，并且由于卡死发生在校验早期，连一条可操作的错误提示都得不到。

### 6.3 产品要求

1. **合法参数必须通过**：我们自己写出的默认参数（64 MiB / t=3 / p=4，`:14-16`）以及历史版本可能写过的任何参数组合必须继续通过——钳制上限必须显著高于既有写入面，宁可宽松也不能拒收自家旧备份。
2. **异常过大的派生参数必须在派生开始前被拒绝**：返回「无法校验/无法解密」类错误（fail-closed，与未知 KDF 同路），不尝试分配内存，错误在亚秒级返回。
3. **错误必须人话化**：映射到「该云端文件的加密参数异常，可能已损坏或由不兼容的版本写入」一类可操作文案，并复用现有「标记损坏 fail-closed」的 UI 通道；不得把内部参数值直接抛给用户。
4. **两条路径同一套上限**：校验子路径与 DSBK 文件头路径共用同一组常量与同一段判断，避免只堵一半。
5. **上限常量必须有注释说明取值依据**（覆盖历史写入面 + 合理硬件余量），并在本目录登记，未来放宽只许向上。
