# AI 驱动的大型技术栈迁移：编排与协调者设计（蓝图）

适用：几十条并行 AI 会话、数周时间、几十万到百万行代码的技术栈转换（语言/框架/运行时更换、单体拆插件等）。
本文不绑定具体工具；"本项目"指 Deep Student 从 Tauri + Rust 迁移到 Electron + Node（约 60 条 lane、4 个协调者，2026-11），
其数字来自 `audits/W11-coordinator-diagnosis.md`。

---

## 0. 五条原则

1. **检测不等于处理。** 每个检测器都必须连着一个动作（自动执行，或交给有权限的明确角色），否则它只是在生产噪声。
   本项目：卡住检测 90 秒就能触发，但 44 段超过 10 分钟的卡住只有 3 段得到干预。
2. **谁负责一类状态，谁就要有能改变那类状态的执行器。** 只能"发消息"的协调者会退化成催办器。
   本项目：134 个 `.git` 文件被 root 占住，所有协调者都没有权限和动作去修。
3. **度量产出，不度量活动。** 进程活着、有输出、有提交，都不代表有进展；度量必须能区分产品代码、测试、文档和自动检查点。
   本项目：main 上 53% 的提交是自动检查点，执行者有改动的轮次里 38% 只改文档。
4. **数字不动时先问"统计对不对"，再问"做没做"。** 指标口径错了，最勤奋的 agent 会去满足口径而不是交付。
   本项目：命令 B 级要求逐条勾 SPEC，代码完成后 B 级仍 0% 达 47 小时，大量轮次用来补文档。
5. **规则必须由工具执行。** 写在提示词和运行手册里的"不要重复催办"不会自己生效。

## 1. 角色与权限

| 角色 | 职责 | 必须能直接执行的动作 | 不做 |
|---|---|---|---|
| 执行者（每工作包一个新会话） | 在单一所有权范围内完成一个可独立验收的工作包 | 提交、自检、交付报告 | 跨范围改动、改验收标准 |
| 评审者 | 独立抽检，逐条对照源实现 | 退回、要求回滚 | 自己修 |
| 计划协调者 | 拆包、派发、依赖收口、语义裁定 | 派发 / 改派 / 拆包 / 停放 / 换模型 | 写产品代码 |
| 集成验证协调者 | main 常绿、集成、全量测试、账本、门禁误报 | 指定批次集成、回退坏提交、隔离误报、批准例外 | 改质量标准 |
| 监督者（总指挥） | 对"阻塞是否在减少"负责；找卡点、选动作 | 修复动作（auto 级）、重启 lane、指定集成、暂停/恢复派发、收回过期锁 | 写代码、改看板中别人的写面 |
| 管线工程师 | 编排代码本身 | 改编排代码并带自测 | 业务代码 |
| 特权运维代理（root，非 LLM） | 已知控制故障、属主/资源/服务 | 白名单内的特权动作 | 执行仓库代码、做语义判断 |
| 人 | 保留事项：发布资源、证书、删数据、改完成定义 | — | 日常调度 |

设计要点：
- **单写者**：每个状态文件、每个看板文件、每条分支只有一个写者；守护进程是调度状态的唯一写者，其他人经信箱提请求。
- **权限分层**：LLM 角色在普通用户下运行；需要 root 的动作由一个**不执行仓库代码**的特权代理按白名单完成（仓库对普通用户可写，root 执行仓库脚本等于提权）。
- **监督者不是传话筒**：它的合同里必须列出它能执行的动作；如果只有"发消息"，就会出现本项目那种 140 段指挥日志、7 次"接管调度"却无从接管的情况。

## 2. 工作单元

- 工作包 = 一个所有权范围 + 一个会话（目标 ≤2 小时、上下文 ≤250K）+ 一组可机器核对的验收条件。
- 交付物是**证据**：提交号、自检 job id 与退出码、受影响测试的 passed/failed/skipped 计数、需要时的差分/录制 run id。
- 跨范围需求写进交付报告的"阻塞"，由计划协调者转成提供方的工作包，不允许 lane 之间点对点派活（本项目 v2 曾有约 970 条点对点需求无人收口）。
- 会话卫生：上下文超过阈值换新会话；会话被内容过滤连续拦截换新会话；"继续"类固定续派提示默认关闭（本项目 400 次自动续派里只有一半在 1 小时内产生了提交，且多为检查点）。

## 3. 度量体系

### 3.1 三层完成度

| 层 | 问题 | 例子 | 只看这一层的风险 |
|---|---|---|---|
| L1 存在 | 有没有实现/注册/映射 | 命令已注册、测试标题对上源测试 | 注册了但调用不到；映射了但没有断言 |
| L2 可达 | 生产入口能不能走到 | 前端调用点 → IPC → 服务 → 存储，参数键与事件名一致 | 单测全绿而功能不可用 |
| L3 行为 | 端到端行为是否与源一致 | 差分录制、golden、真实流程冒烟 | 证据不可追溯就等于没有 |

本项目账本只覆盖 L1（"1058 个命令是否注册"）。Agent 工具执行器约 30 个未实现、前端参数键写错、事件无发射点、缺权限拦截、>2GiB 备份不能导入，
在看板和指挥日志里一次都没出现过。**每一层都要有自己的探针**，至少：L2 用静态调用图 + 契约比对（前端调用的键/事件 vs 后端声明），L3 用少量真实流程冒烟。

### 3.2 口径规则

- 每个指标写清分子、分母、数据源和**它不代表什么**。
- 同源：账本、全测、差分必须标注所依据的提交号；不同源的数字不能互相印证，也不能相加。
- "没做 vs 没统计"自动对账：A 级已满而 B 级长期为 0、测试数据来自一次红的全测、账本基于的提交与最新全测不同——都先报"口径/数据源问题"。
- 反注水：只改映射/文档/报告、自动检查点、重复合入、"合入 N 个提交但净代码 0"，一律不计入进展。

### 3.3 领先与滞后指标

- 滞后：账本、全测通过率、差分 equal 率。
- 领先（每条 lane、每 1–2 小时）：产品提交数、文档提交数、检查点数、消耗步骤数、门禁通过率、集成合入数。
- 管线：集成轮 0 合入连续数、积压候选数、全测落后 main 的提交数、结构故障数。

## 4. 监控：四层信号

| 层 | 信号 | 典型检测器 | 处置（必须有） |
|---|---|---|---|
| 存活 | 进程在、心跳新、有输出 | 心跳文件、无事件 N 秒且无工具进程 | 原会话重启（有次数上限）→ 换会话 → 通知 owner |
| 进展 | 有产品代码/测试提交、步骤换来了提交 | 每 lane 产出分类（产品/文档/检查点/步骤） | 空转：先查结构阻塞，再换会话或改派；只改文档：要求代码交付或说明 |
| 质量 | 门禁、全测、差分、可达性 | 门禁原件、全测 raw 退出码与缺片、契约比对 | 按根因聚类派最小修复包；环境/工具问题与产品问题分开 |
| 结构 | 管线自身：属主、锁、状态文件、磁盘、配置漂移 | 修复动作库的 `detect()` | auto 级自动修；confirm 级给计划 |

去噪规则：
- **拉取优先**：状态写文件，协调者每次唤醒时读到一份摘要；只有"需要某人动作"的事才推送。
- **推送必须去重并带上限**：同一事件同一接收者在窗口内只推一次。本项目卡住汇总 359 条里 354 条是重复，结果整个推送通道被关闭，长卡住从此无人知道。
- **把"活着但没产出"当一等故障**：它不会触发任何存活类报警。

## 5. 自愈：修复动作库

### 5.1 动作规范

每个动作实现四个函数，并满足五条约束：

```
detect()  → findings          只读；为空 = 健康
plan(f)   → steps             可读的执行计划
apply(f)  → result            执行；之后 detect() 必须为空
audit     → repairs.jsonl     谁、为什么、发现了什么（计数+样本）、做了什么、结果
```

1. **幂等**：重复执行没有新副作用。
2. **不删除**：坏文件隔离到 quarantine，旧状态归档；证据、补丁、原始轨迹、数据库永不按年龄删除。
3. **分级**：auto（不改变调度/验收语义）/ confirm（改变语义，需人或集成协调者批准）/ forbidden（结束活任务、清未知 WIP、改验收标准）。
4. **前置条件**：例如"守护进程停止时才能压缩它的状态文件"；不满足就拒绝并说明。
5. **复核**：执行后再跑一次 detect，结果写进审计。

本项目已实现的动作：文件属主修复、状态文件损坏隔离与恢复、调度状态压缩、残留 pid 锁（含 pid 复用）、孤儿全量测试按已提交作业恢复。
值得在新项目一开始就具备的：回放丢失的作业结果、隔离卡死进程组（先 SIGSTOP 取证再决定）、回滚有问题的集成（`git revert`，经集成租约）、磁盘回收（只回收受控目录）。

### 5.2 特权代理

- **能不用 root 就不用 root**：巡检以普通用户运行，代码装在 root 属主路径；需要的特权动作逐条写进 sudoers（精确命令行、无通配符），
  其余一律没有。agent 可写的一切（仓库、`.git`、工作树、状态目录、临时目录）对特权代码都是不可信输入：root 不跟随其中的链接、
  不执行或 import 其中的代码、不在其中跑 git（`core.fsmonitor` 等配置可执行任意命令）、不把其中的内容拷到别处。
- 普通用户身份的巡检也按不可信输入处理：`O_NOFOLLOW|O_NONBLOCK` 打开、只读普通文件、有大小上限；输出用随机名 `O_EXCL` 创建再 rename；
  删除目录用 dir_fd 相对操作并拒绝符号链接顶层；每个动作前先持久化熔断计数，所有命令共享一个短于单元超时的时间预算。
- 只处理白名单：服务状态、心跳、资源快照、受控临时目录；属主漂移只报告，人工一次性修复。
- **意图显式化**：有意停止 = 写 hold 文件；维护标记存在时不做任何启动/重启/恢复。不从 `Result=` 推断（停止超时被 SIGKILL 是 timeout，`Restart=on-failure` 的干净退出是 success）。
- **退避 + 熔断**：同一服务 2 小时内拉起 3 次、调度器心跳停滞重启 2 次后停止自动处理并通知——再重启只会掩盖 bug。
- **诊断先行**：重启前保存 `/proc/<pid>/{status,wchan,stack}`、两次采样的 CPU 时间差（0 = 阻塞，接近满 = 死循环）、日志尾部。

本项目的反例：旧巡检"inactive 10 分钟就拉起、心跳超 15 分钟就重启"，调度器被人停掉时也会每 30 分钟被拉起一次；维护脚本以 root 跑 git，
留下 134 个 root 属主文件，6 分钟后 lane 提交开始失败。

## 6. 推进机制

### 6.1 协调者工作循环（每次唤醒）

1. 读摘要（存活/进展/质量/结构四层 + 上轮"下轮要验证什么"）。
2. 选 ≤3 个阻塞，**按影响排序**：挡住 main/集成 > 挡住多条 lane 的共同根因 > 单条 lane。
3. 每个阻塞归类并用该类的第一选择：

   | 类别 | 第一选择 | 其次 |
   |---|---|---|
   | 结构 | 执行修复动作 | 交有权限的角色（附计划） |
   | 流动 | 调度动作：重启、指定集成、收回过期锁、暂停派发 | 改派 / 拆包 |
   | 交付 | 给**唯一** owner：期限 + 可验证产物 | 第 2 次无新证据：换 owner 或换动作 |
   | 口径 | 修判据或数据源 | — （禁止派人补文档凑数） |
   | 保留 | 写入"待用户裁定"，其余照常 | — |

4. 写 ≤8 行日志：动作、指令、上轮兑现、下轮验证。无变化只写一行。

### 6.2 升级阶梯（由工具执行）

| 次数（同一主题、同一接收者、2 小时内） | 允许 |
|---|---|
| 第 1 次 | 具体指令 + 期限 + 可验证产物 |
| 第 2 次 | 允许，但工具提示"下一次将被拒" |
| 第 3 次且无新证据（提交号/job id/run id） | **工具拒绝发送**，返回下一步：自己执行动作 / 换 owner / 写待用户裁定；确有新事实需写明理由并记审计 |

本项目回放：这条闸门会拒绝 C0 214 条消息中的 4 条、C1/C2 各 1 条，全部是真实重复，误拦很低。阈值可调，但必须存在。

### 6.3 对下属的验收

- 代码：提交号 + 自检 job id 与退出码 + 测试计数。
- 集成：合入记录或拒绝原因。
- 结构：detect 复查为空。
- 决定：决定编号。
- 产物没到就是没完成；"已交付"≠"已集成"≠"已验收"。

### 6.4 防止"刷文档代替交付"

- 指标里文档不计分；进展摘要把"只改文档"的 lane 单独列出。
- 协调者日志限长；看板只记决定和事实，不复述历史。本项目协调者 56% 的轮次只改看板/文档，看板累计 1.27MB。
- 口径错误由协调者修，不转嫁成执行者的文档任务。

## 7. 证据规范

| 证据 | 必含字段 | 失效条件 |
|---|---|---|
| 提交 | SHA、所属工作包 | 不在 main 上不算集成 |
| 自检/门禁 | job id、命令、raw 退出码与信号、源码前后 head | 验证期间源码变化 |
| 全量测试 | run id、受测 head、每片 job id 与 raw 退出码、缺片列表 | 混片、缺片、raw 非 0 判绿、用新 main 的映射配旧结果 |
| 差分/录制 | 两端各自的提交号与构建回执、输入语料哈希、归一化规则哈希 | 任一端版本缺失（本项目 G3 1043 组对比因缺 B 端提交号不能作验收证据） |
| 账本 | 计算所依据的 head、所用全测 run id | 与全测不同源 |
| 修复动作 | 动作、发起者、发现计数与样本、结果、复核 | 无复核 |

环境与产品分开：测试失败先判断是否由执行环境造成（本项目全测 6 个失败来自作业临时目录落在隐藏路径，被产品的隐藏路径检查拒绝）。

## 8. 常见失败模式与对策

| 失败模式 | 症状 | 根因 | 检测 | 对策 | 本项目 |
|---|---|---|---|---|---|
| 检测而不处置 | 告警很多、问题持续 | 检测器不连动作 | 告警→动作的比例 | 每个检测器配动作和 owner | 44 段长卡住 3 段被处理 |
| 催办空转 | 同一指令反复出现 | 协调者只有消息手段 | 同主题重复率 | 工具化升级阶梯；给监督者执行器 | WP-043 → C1 7 次 |
| 刷文档 | 文档提交多、代码少 | 指标奖励文档；口径要求文档 | 每 lane 产出分类 | 文档不计分；修口径 | 38% 有改动轮次只改文档 |
| 度量失真 | 数字长期不动或虚高 | 判据、数据源或基线不同源 | 自动对账 | 指标声明"不代表什么"；同源校验 | B 级 0% 达 47 小时；仓库账本停在 3 天前 |
| 覆盖盲区 | 指标好看、功能不可用 | 只度量 L1 | L2/L3 探针 | 三层完成度 | 约 30 个工具执行器未实现无人发现 |
| 结构故障无人修 | 某类操作持续失败 | 权限在 LLM 角色之外 | 结构检测 | 特权代理 + 修复动作库 | root 属主 134 文件 |
| 盲目自愈 | 服务被反复拉起、bug 被掩盖 | 无意图感知、无熔断 | 重启次数 | 意图感知、退避、熔断、诊断先行 | 停掉的调度器会被拉起 |
| 状态文件腐化 | 行为悄悄改变 | 读方回落默认值 | 状态校验 | 隔离+恢复，语义类需确认 | 暂停文件损坏 = 派发恢复 |
| 状态膨胀 | 每轮变慢、备份成倍 | 只追加不归档 | 大小阈值 | 定期归档 | 调度状态 7.6MB + 5 份备份 |
| 噪声导致关闭通道 | 推送被整体禁用 | 无去重 | 推送重复率 | 去重 + 上限 + 拉取优先 | 359 条汇总 354 条重复 |
| 证据不可追溯 | 大量产物不能用于验收 | 未记录版本 | 证据清单校验 | 运行前冻结并记录两端版本 | 12GB 录制缺 B 端提交号 |
| 环境被当产品问题 | 修产品修不好 | 执行环境差异 | 失败分类 | 先排除环境 | 隐藏 TMPDIR |
| 资源挤兑 | 大批跑挂起、整机卡 | 并发无准入 | 资源准入 | 准入控制、托管进程组、有终态记录 | 42 worker 批跑挂起被人工停 |
| 清理过宽 | 证据被删 | 按年龄清理 | — | 只清理受控目录 | 早期 /tmp 按年龄清理 |
| 维护操作破坏现场 | 维护后新故障 | 以 root 操作普通用户仓库 | 结构检测 | 维护降权 + 维护标记 + 事后检测 | root git → X7 提交失败 |

## 9. 落地清单

**启动前**
- [ ] 角色权限矩阵，每个角色列出可执行动作；监督者有执行器。
- [ ] 三层完成度各有至少一个探针；指标写明口径与"不代表什么"。
- [ ] 证据字段规范；全测/差分记录两端版本。
