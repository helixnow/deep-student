# 迁移质量标准 v2（2026-11-04 起生效，优先于 quality.md 中与之冲突的条目）

## 为什么要有 v2

截至 2026-11-04，独立复核出了 17 份验收报告，只有 2 份通过，"必须修复"项超过 100 条。
抽查确认复核结论准确。问题有两个根源：

1. **逐函数局部翻译。** 实现者只看眼前的函数，看不到 serde 规则、Drop 清理、日志、表所有权、
   取消语义这些横切约束。
2. **指标只量形式。** 旧 A 级只要求"命令注册了 + 有带 Rust 测试名的测试文件"。实现者会朝指标
   优化：函数和测试都写了，生产链里却没人调用；测试被改到能让实现通过为止。

v2 从源头处理：先定义什么叫完成，再把测试和实现分开，并按能力分配角色。

## 0. 原则

- **完成 = 生产路径上的行为与 Rust 等价，并且有证据。** "注册了""测试绿了"本身都不算完成。
- **证据按强度排序：**
  1. 差分对照：同一输入，Rust 与 TS 各跑一次，比较返回值、数据库变化、事件。
  2. 走生产入口的移植测试：通过 kernel 或命令入口调用。
  3. 对照 Rust 源码逐分支审读。
  能拿到更强的证据，就不要停在更弱的那一级。
- **测试不为实现让路。** 移植测试的断言必须与 Rust 原断言逐条对应：数量、取值、方向都一致。
  实现过不了测试，就改实现，不改测试。改动既有移植测试时，提交信息里必须逐条写明对应的 Rust 断言和改动理由。
- **不确定就停。** 找不到 Rust 对应语义，或需要别人的接口时，写进 BLOCKERS.md 并通知协调者。
  不准猜，不准用替身冒充，不准静默降级。
- **宁可少而对，不要多而错。** 一条命令做到 v2 完成清单，比十条"能跑"的命令更有价值。

## 1. 八类已知问题的硬规则（每类都附自检方法）

### 1.1 生产接线：测试必须测生产代码
- 移植测试中的被测符号，必须能从插件 `index.ts` 的 `register` 或 `provide` 静态到达。
  优先通过 kernel 或命令入口调用。
- 自检：对每个导出函数，找到它的生产调用点（文件:行）。找不到，相关测试就不能标 ported。

### 1.2 单一所有者
- 只写本插件拥有的表和文件。写他人的数据，一律经对方 `api.ts` 发布的方法；需要事务的用
  `*WithConn`（D1）。
- 不复制他人的仓储或实现。
- 自检：`rg "INSERT|UPDATE|DELETE|REPLACE" <你的插件>`，确认每张表都归你。

### 1.3 数据边界：严格对齐 serde
- 一切入站数据都必须经过解码器，严格按 Rust serde 规则处理：
  - 入站数据包括：持久化 JSON、设置值、IPC 入参、文件。
  - `rename_all`（camelCase / snake_case 逐字段核对）、
  - `#[serde(default)]` 与必填字段、`Option` 与缺省、`deny_unknown_fields`、
  - 枚举的标签形式、整数宽度。
- 禁止 `JSON.parse(x) as T`、`as unknown as T` 这类无校验断言。
- i64 / u64 超过 2^53 时按 D3 处理，不得经过 `Number` 丢精度。
- 出站形状与 Rust `serde_json` 输出逐字段一致：不多出 null 字段，也不少字段。
- 自检：对每个持久化或 IPC 结构，打开 Rust 的 struct 定义，逐字段核对名字、可选性、类型。

### 1.4 日志与错误
- Rust 的每个 `warn!` / `error!`（以及有业务含义的 `info!`），在 TS 对应位置都要有 host logger 调用：
  级别相同，关键字段相同。
- 错误类型、消息前缀、上下文、抛出顺序与 Rust 一致。
- 不得吞错。best-effort 的分支保持 best-effort，fail-fast 的分支保持 fail-fast。
- 自检：`rg "warn!|error!" <Rust 源文件>`，逐条在 TS 中找到对应调用。

### 1.5 测试真实性
- 不弱化断言，不测替身，不测未接线的副本。
- 暂时做不到的测试如实标 `pending`，并写明缺什么、由谁提供。
- 自检：Rust 测试的 `assert*` 数量 ≤ TS 对应测试的 `expect` 数量，且逐条有对应。

### 1.6 完整性：不只做主路径
- Rust 的每个分支在 TS 都要有对应：`match` 分支、`if` / `else`、`?` 的错误传播、`cfg` 平台分支。
- 自检：SPEC.md 中该命令一节列出分支表（Rust 文件:行 → TS 文件:行），每个分支都有落点。

### 1.7 运行时语义
- Drop / RAII 清理 → `try/finally` 或 `using`。所有退出路径（包括抛错）都要清理。
- 测量时长用单调时钟 `performance.now()`。只有 Rust 用墙钟（`SystemTime`）的地方才用 `Date.now()`。
- CPU 密集或同步 IO（ZIP、哈希、大文件、图像）不得阻塞 Host 事件循环，放到 worker。
- 取消语义：`AbortSignal` 贯穿到底，与 Rust 的 cancel token / drop future 行为一致。
- 并发：锁、单写者、事务边界与 Rust 一致。
- 平台：`cfg(target_os)` 分支逐一对应；Windows 的文件身份、路径大小写、换行都要处理。

### 1.8 闭环：修了要复验
- 修复复核项时，提交信息写 finding ID（如 `fix(L02-01): …`）。
- 合入 main 后，由协调者通知对应复核人复验签收。签收之前，这一项不算完成。

## 2. 每条命令的完成清单（写进 SPEC.md 该命令一节）

- [ ] Rust 入口位置（文件:行）与 TS 入口位置
- [ ] 分支表：Rust 每个分支 → TS 落点
- [ ] 数据边界：入参、出参、持久化结构的解码器，以及与 Rust struct 的逐字段核对结论
- [ ] 日志映射：Rust 的 `warn!` / `error!` → TS logger 调用
- [ ] 错误映射：错误类型、前缀、顺序
- [ ] 所有权：读写了哪些表，各归谁
- [ ] 运行时语义：清理、取消、时钟、阻塞、平台
- [ ] 测试：经生产入口调用；断言与 Rust 逐条对应；pending 项如实标注
- [ ] 证据等级：差分 / 生产入口测试 / 审读

## 5. 工作流：完成前必须自检（2026-11-04 起）

- 声明某项完成、或一轮工作结束之前，必须先提交全部改动，`git merge --no-edit main`，再运行自检：
  `node /home/dsdev/dev/deep-student/scripts/electron-migration/lane-gate.mjs`
  自检的检查列表与集成门禁是同一份（`lib/gate-checks.mjs`），每项都经作业队列执行。
- 自检通过后，结果按提交记录。集成时，自检通过、且分支头就是自检时那个提交的 lane 优先测试。
- 集成门禁失败、之后又没有新提交的分支，下一轮不再重复测试（3 小时后放行一次）。修复后重新自检即可。
- lane 正常结束后，如果协调者 10 分钟内没有新指令，系统会自动续派。续派的顺序是：先处理反馈，再自检，再做剩余事项，最后按 v2 自查一轮。
  确实没有剩余工作时，在 LANE.md 写明证据，并回复"无剩余工作"。
