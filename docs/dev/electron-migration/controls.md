# 迁移管控体系

目标：在保证效率的前提下，让迁移结果**可用、可靠、与 Rust 一致**，新架构对齐 DSH 的"一切皆插件"。

管控的出发点是抽检中观察到的模型缺点（见 quality.md）：
- 不会判断"整件事做完了没有"，容易提前收工；
- 移植了却没接入生产路径；
- 代码里没写明的隐式语义（库默认行为、日志、事务）容易丢；
- 会钻门禁的空子；
- 倾向于重复实现，而不是复用已有模块。

对策分四层。**拦截**只用于客观、低成本、信号强的问题；启发式发现的问题**只反馈、不拦截**，以免门禁过严拖慢进度。

## 1. 提示：把容易出错的步骤变成必经步骤

派发提示里的「单元工作协议」和「完成协议」（见 `dispatch/*.md`）把每个命令或函数的迁移固定为 7 步：
1. 列出行为清单；
2. 移植测试；
3. 实现；
4. 补日志与副作用；
5. 接入生产路径；
6. 自检；
7. 提交。

完成报告必须粘贴机器输出（ledger、wiring、strict 边界），不接受自述的"已完成"。「钻空子对照表」列出了每种被禁止的捷径，以及对应的正确做法。

## 2. 门禁：拦截合入 main（集成工作树中试合并）

| 检查 | 理由 |
|---|---|
| 改动不越出本 lane 的路径 | 所有权是并行的前提 |
| `tsc` 类型检查 | 客观、便宜 |
| 边界检查（插件间只经 `api.ts`、SQL 只在 repository/、原生依赖只在平台层、无 mock/TODO、无空 catch） | 架构正确性，误报极少 |
| **strict 边界（2026-11-03 17:00 UTC 起）**：`console.*`、只含 `void` 的 catch | 日志丢失与规避扫描已被反复观察到，提前公告后启用 |
| **本次改动涉及目录的测试必须通过** | 只跑受影响的目录，控制耗时 |

分支最新提交如果是 WIP 检查点、门禁过不了，会回退到 lane 最近一次自己的提交再试；lane 自有文档（LANE/SPEC/TESTMAP）的冲突以 lane 的版本为准。

## 3. 度量：只看机器算出来的数字

- ledger A/B/C：命令 A 级要求已注册、有契约、内核覆盖检查通过；测试 A 级要求测试存在、标题对应 Rust 测试名、**被测模块已接入生产路径**（wiring）。
- `obsolete` 必须有协调者在 `migration/approvals.json` 中的批准。

## 4. 反馈：及时发现，精确到行

- **自动质量反馈**（`quality-feedback.mjs`，每次自动集成后运行）：把 strict 违规、未接线、平台模块已发布后仍保留的本地重复实现、超大文件、测试被削弱（断言数下降、`.skip`、删除测试文件）这些问题，**只把新出现的**、带 `file:line` 排入对应 lane 的队列。
- **独立抽检**（协调者每 2–3 小时一轮）：只读审查者逐行对照 Rust，结论写入 quality.md 和各 lane 的整改清单；高风险问题用 `interrupt` 立即打断处理。
- **守护进程**：检查点、供应商故障恢复、额度换号、自动集成，以及按队列在 lane 收尾后续派指令。

## 5. 架构：对齐 DSH "一切皆插件"

- 每个业务域是一个 Cordis 插件：`index.ts` 只做接线，能力通过 `api.ts` 中版本化的服务提供，跨插件只经服务调用。
- 生成**能力目录**（服务、提供方、消费方、命令、事件），对标 DSH 的 capability-seams，供社区开发者查阅。
- 插件 SDK 文档，加上一个**社区插件替换官方服务**的可运行示例（profile 中同 id 覆盖），并进入测试。
- 门禁保证服务边界不被绕过，生态的可替换性才有保障。
