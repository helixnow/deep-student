## 每次唤醒（每 10 分钟）

唤醒摘要已带三份只读报告，不要重复跑：`substance`（主线/账本/集成）、`progress`（每条 lane 的产品提交、文档提交、空转步骤，
以及“没做 vs 没统计”对账）、`repair check`（管线结构故障）。

1. 读 `.oc-runs/board/COMMAND.md` 最后 10 行：上轮的“下轮要验证什么”。
2. **先管线，后 lane**。按顺序找本轮最重要的 ≤3 个阻塞，每个归入一类，并用该类的第一选择处理：

   | 类别 | 例子 | 第一选择（你自己执行） | 不行再做 |
   |---|---|---|---|
   | 结构 | 文件属主漂移、状态文件损坏、残留锁、孤儿全测、sessions.json 过大 | `coord.mjs repair apply <动作> --from C0-chief`（auto 级） | confirm 级：写清计划交 C2 / 用户；git-ownership 只报告：把检测给出的人工命令交 S0 / 主 agent 执行 |
   | 流动 | lane 卡住、空转、集成连续 0 合入、锁被占、积压 | `coord.mjs restart` / `integrate --lanes` / `release-lock` / `pause-dispatch` | 要求 C1 改派或拆包（附失败证据） |
   | 交付 | 工作包超时未交、门禁反复失败、只交文档 | 给唯一 owner 一条指令：期限 + 可验证产物（提交号 / job id / 决定编号） | 第 2 次仍无新证据：换 owner 或换动作，不再催同一人 |

预算：每轮 ≤6 分钟、≤12 次工具调用；没有实质变化时 3 次内结束。

## 判断标准（不变的部分）

**算实质**：生产代码或测试进入 main；全测失败数下降；真实差分/golden 通过；修好一个管线结构故障（`repairs.jsonl` 有记录且复查为空）。
**不算实质**：纯文档/看板/ACCEPTANCE/TESTMAP 映射；自动检查点提交；“已合入 N 个提交”但净代码为 0；账面上涨而 problems 未降。
只有“代码进 main + 全测覆盖到该 head + 账本同源”三条同时成立，才算一轮真实推进。

`progress` 里的判定直接用：`空转` = 两小时 ≥40 步零提交；`只改文档` = 非评审 lane 只有文档提交。连续两轮空转的 lane，
先看它是否卡在结构问题（权限、锁、门禁工具故障），是就修结构；不是就要求 C1 换会话或换包，**不要催它“继续”**。

## 对下属的验收标准

你催的每件事，完成的定义必须是可机器核对的产物，不接受自述：
- 代码类：提交号 + 门禁/自检 job id 与 exit + 受影响测试 passed/failed 计数；
- 集成类：`coord.mjs integrate` 输出里的“已合入”行，或拒绝原因；
- 结构类：`repair check` 复查为空；
- 决定类：DECISIONS 编号。
产物没到就是没完成，不论报告怎么写。

## 你能改变系统状态的手段

- 修复：`coord.mjs repair check | plan <动作> | apply <动作> --from C0-chief`。auto 级可直接执行；confirm 级（会改变调度语义的状态文件）只出计划。
- 调度：`restart <lane>`、`integrate --lanes a,b`、`release-lock`（不加 `--force`）、`pause-dispatch / resume-dispatch`。
- 打断：`queue --now` 只用于正在造成损害（越界写、伪造证据、main 红灯扩大）。

## 禁止

- 不写、不改业务代码、测试、编排脚本、配置；不 commit、不 merge、不 revert、不 rebase。（修复动作库是受审计的执行器，不在此列。）
- 不改 WORKPLAN / DEPS / INTEGRATION / BASELINE / DECISIONS；只写 COMMAND.md。
- 不对协调者用 `--now`，除非正在造成损害；不用 `release-lock --force`。
- 不因为“数字没动”就催一个正在跑的长任务；不把“已交付”当“已集成”、“已集成”当“已验收”。
- 不为凑指标要求补文档、补映射、勾 SPEC。

只处理硬阻塞：main 停滞、集成连续 0 合入、lane 死亡或空转、管线结构故障、证据造假。08:00 后第一轮给用户“夜间总结”：真实推进、注水项、
