### 4. 设计论证补强（本席新增，非缺陷）

超载剥除可能把 tools 段 marker 剥到零（如超载用例终态），这**不构成缓存
损失**：Anthropic 前缀缓存按 tools → system → messages 顺序累积，任何
system 块级断点覆盖的前缀天然包含全部 tools 字节——只要 system 侧仍有
marker 存活（剥除序保证 system 后剥），tools 前缀就仍被缓存锚定。
「前剥后保」不只是价值排序正确，在这个具体形态下是零损剥除。
此论证 r5 两份文档均未写明，补录备后续轮引用。

## 五、遗留项重验（全部维持 #6 定性，无升降级）

### 1. 误剥向量：保险打点先于核算 —— 仍潜伏、仍不可达

代码顺序重验：system 尾保险 `:2384-2388` 与 tools 尾保险 `:2403-2407`
均在守卫 `:2414` 之前执行，#6 §二.4 的形态（调用方 3 个显式 tools marker +
非空未打点 system → 自动保险制造超载 → 剥掉调用方最靠前的显式 marker）
在当前代码中依然成立。可达性重验：唯一生产打点方 `model2_pipeline.rs:4046`
（r5 后行号，原 :3665）仍是 1 个 system 块级 marker（`:2687-2694` 的同形
fixture 是测试夹具不计），真实流量块级合计 = 1 system + 1 tools 尾保险 = 2 ≤ 3，
守卫纯守护。修法建议维持 #6 原案（保险打点预算感知化，改动最小），
本席无 mod.rs 补丁权，移交。

### 2. system 剥除循环零测试覆盖 —— 仍零

本席 grep：三条 P2 测试的剥除全部由 tools 循环消化，无任何用例让 overflow
穿透进 system 循环（`:2961-2970`），也无 tools 为 None 的纯 system 超载用例。
「system 内靠前块先剥」仍是注释承诺而非被测行为。建议验证轮补 1 条穿透
用例（如 tools 1 marker + system 4 marker → 剥 tools 1 + system 首块 1）。

### 3. `Value::Null` 透传微瑕 —— 仍开、内部自洽

`.cloned()` 不校验值形状，`"cache_control": null` 会得 `Some(Value::Null)`。
重验一致性：`has_marker`（`is_some`）、守卫计数（`get(...).is_some()` /
`is_some`）、剥除（`take()` / `remove()`）三处对 Null 的口径**彼此一致**
（都当 marker），不会导致计数与剥除错位；唯一暴露面是序列化出
`"cache_control": null` 上线可能被 API 拒。R2 遗留、非 r5 引入，定性不变。

### 4. automatic 异 TTL 400 面 —— 仍开

`CacheControl` 结构仅 `cache_type` 一个字段（`:2496-2498` 注入处重验），
调用方透传带 `"ttl":"1h"` 的块级 marker 且恰在末块时与无 ttl 的 automatic
异 TTL 冲突（#6 §二.5 官方文档结论）。与四槽预算正交，归后续调研卡，不变。
