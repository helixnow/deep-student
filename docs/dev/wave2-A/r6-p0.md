## 一、断点形状与落位 —— 确认

### 1. 形状

`convert_to_responses_format_for_endpoint`（`:1453`）在双门控成立时于
`input[0]` 插入 developer 消息，断点打在其 `input_text` 块上：

```1555:1567:src-tauri/src/providers/mod.rs
        if instructions_as_developer_breakpoint {
            input_blocks.insert(
                0,
                json!({
                    "role": "developer",
                    "content": [{
                        "type": "input_text",
                        "text": instructions.join("\n\n"),
                        "prompt_cache_breakpoint": { "mode": "explicit" }
                    }]
                }),
            );
        }
```

与官方文档（r1 台账 S1/S2/S9）「块级 `prompt_cache_breakpoint:
{"mode":"explicit"}`，顶层 instructions 不可打断点、稳定指令放 developer
message 的 input_text」完全一致。多条 system 消息以 `\n\n` join 进单块、
打单断点，方案自洽。门控不满足时回落顶层 `instructions`（`:1582-1584`），
两条路径互斥（`!instructions_as_developer_breakpoint` 守卫），不会出现
「developer 块 + 顶层 instructions 双发」的形状。

预算面：单断点方案 = implicit 默认断点 1 槽 + explicit 1 槽 = 2/4 写槽，
远低于官方 4 写槽上限；断点只打在 developer 块，天然规避 S13
`function_call_output` 零写入陷阱。均与 r1 结论一致，维持。

### 2. 双门控

- **模型门控** `model_supports_prompt_cache_breakpoint`（`:723-756`）：
  取 `/` 分段后的型号段、强制 `gpt-` 前缀锚定，major > 5 直接过
  （后缀限空 / `-` / `_` / `.数字`），major == 5 要求 `.minor` 且
  minor ≥ 6、后缀限空 / `-` / `_`。本席逐分支手推：`not-gpt-5.6` 与
  `deployment-not-gpt-6-preview` 因前缀锚定必拒，`gpt-5.10` 按整数
  10 ≥ 6 正确通过（不是字符串比较），大小写经 `to_ascii_lowercase`
  归一。实现与注释（`:721-722`「只解析完整 GPT 型号段」）一致。
- **端点门控** `endpoint_supports_prompt_cache_breakpoint`（`:758-760`）
  → `is_official_openai_api_endpoint`（`:130-135`）：`url::Url` 解析后
  host 精确等于 `api.openai.com`，解析失败（空串、无 scheme）fail-closed。
  与 stream_options 门控共用同一函数，语义一处维护。

## 二、三类主快照 `:5194` —— 逐字段静态推演，确认会绿

`openai_responses_prompt_cache_breakpoint_wire_bodies_are_capability_gated`
用整包 `assert_eq!` 钉死三类 wire body。因本轮铁律只写不跑，本席对三段
期望值逐字段对照转换器实现做了模拟执行：

**类 1：官方端点 + gpt-5.6**（`:5202-5230`）
期望 6 键 `model/input/stream/store/reasoning/include`：

- `input[0]` developer 断点块：门控双真 → `:1556-1566` 插入，形状同上；
- `input[1]` user 块：字符串 `"hi"` 经 `push_message_parts`（`:850-855`）
  → `[{"type":"input_text","text":"hi"}]`；
- `stream: true`：body 无 stream，`:1571` 缺省 true；
- `store: false`：body 无 store，`:1580` 缺省 false；
- 无顶层 `instructions`：`:1582` 条件被 developer 路径排除；
- `reasoning: {"summary":"auto"}`：body 无 reasoning 键 → else 分支
  `:1598-1611`，`"gpt-5.6"` contains `"gpt-5"` 命中，无 reasoning_effort
  不加 effort；
- `include: ["reasoning.encrypted_content"]`：`:1617-1625` 同 substring 命中；
- 不会多出别的键：body 无 max_tokens / temperature / response_format /
  verbosity / tools / tool_choice / parallel_tool_calls；
  `preserves_provider_reasoning_extensions`（`:1681`）对 api.openai.com
  为 false 且 body 无 thinking 键。`serde_json::Value` 对象相等按键值
  集合比较、与书写顺序无关，整包相等成立。

**类 2：第三方网关 + 同模型**（`:5232-5252`）
仅端点门控翻 false → developer 块不插、system 回落顶层
`instructions`；`reasoning` 与 `include` 是纯模型门控（与端点无关），
仍存在——期望体两者都写了，正确。

**类 3：官方端点 + 伪名 `deployment-not-gpt-6-preview`**（`:5254-5271`）
模型门控 false → 回落顶层 instructions；且该名不含 `gpt-5`/`codex`/`o1`/
`o3` 子串、非 o1/o3/o4 前缀、无 reasoning_effort → **既无 `reasoning`
也无 `include`**，期望体恰好两者皆缺，正确。这一类同时钉住了「伪名
不触发断点」和「伪名不触发 reasoning 家族字段」两个门，价值最高。

三类合成一条测试的整包断言是刻意的「钉死」：转换器未来任何缺省字段
增删都会三段齐红，逼迫改动者重新核对 wire 形状。脆是代价、也是本卡
口径（见 §五.4 权衡备注）。

## 四、快照层与 wire 层等价性 —— 确认（中心问题）

快照测试直接调 `convert_to_responses_format_for_endpoint` 而非
`build_request`，「快照会不会说谎」取决于两层之间是否还有 body 变换：

- `build_request`（`:1809-1835`）只拼 url、装 header，body 就是转换器
  返回值原样——无第二次变换；
- 转换器入口的 `sanitize_openai_request_body`（`:614-651`）只动
  `tools` / `tool_choice` 两键，对三条测试的无工具 body 是恒等映射，
  不干扰整包相等；
- 上游 `model2_pipeline` 不自造 `prompt_cache_breakpoint`
  （全仓该字符串在 m2p.rs 仅存于 `:3592` 的接线约束注释），适配器是
  生产路径上唯一的断点作者。

结论：快照断言的对象即真实 wire body，测试层无失真。

## 五、观察与备注（均不构成翻案）

1. **调用方块级断点静默丢弃**：`push_message_parts`（`:848` 起）重建
   content 块时只保留 type/text/图像字段，调用方若在消息块上自带
   `prompt_cache_breakpoint` 会被无声剥掉。收益是天然守住 S13 陷阱
   与 4 写槽预算（适配器单一作者制）；代价是 r1 §4 P2 的
   「explicit-only 多断点」优化将来只能改适配器、不能从调用方喂入。
   与 Anthropic 侧 r5 刚开口的 tools `cache_control` 透传形成刻意
   不对称。记入遗留观察，不是缺陷。
2. **解析器保守拒绝面**：补丁号形如 `gpt-5.6.1`（minor 后缀 `.1` 不在
   白名单）、微调 id 形如 `ft:gpt-5.6:…`（`gpt-` 前缀锚定失败）均
   fail-closed 回落顶层 instructions——只损失缓存收益、无 wire 风险。
   官方现名单下无此形态，无需动作；若官方发补丁号再扩。
3. **解析器宽进面**：任意 major > 5（如假想名 `gpt-55`）会被放行。
   这是对官方命名惯性的前瞻押注，且门后行为只是打断点（官方端点上
   未知新模型大概率兼容或明确报错），风险可接受。
4. **整包快照的脆性**：转换器每加一个缺省字段三段全红。这正是
   「钉死」语义，但建议后续改动者把「更新此快照」写进转换器缺省
   字段的改动清单，避免误判为回归。
5. **场外一行**（非 P0 面，不裁决）：`include:
   ["reasoning.encrypted_content"]` 只受模型门控、对未知网关照发
   （类 2 快照已如实钉住），与 stream_options「官方端点才注入防严格
   网关 400」的姿态不对称，归后续 provider 调研卡斟酌。
6. **跨席取证（移交 #9/#10 台账）**：R5-6 翻案的 P1 事件序列测试
   `openai_adapter_choice_completion_keeps_event_sequence_until_done_marker`
   在 tip 已按 #6 给出的一行修法改为
   `usage["prompt_tokens_details"]["cached_tokens"] == json!(8)`
   （`:4001`），喂入数据 `:3984` 与断言键位现已同形。台账 R5-8
   「P1 测试键位错误待修」一项可翻页为已修（未验证）。
