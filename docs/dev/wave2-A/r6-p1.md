## 一、r5 翻案项落地核验：断言键位已改，且在提交内

r5 #6（`r5-review-providers.md` §三）翻案指出：新测试
`openai_adapter_choice_completion_keeps_event_sequence_until_done_marker`
断言 `usage["cached_tokens"] == json!(8)`，但 Chat 适配器把 usage
**原样透传**（`:300-302`），`cached_tokens` 嵌在 `prompt_tokens_details`
之下、顶层取值得 `Value::Null`，执行必挂。

当前 tip 的终态断言：

```3997:4002:src-tauri/src/providers/mod.rs
        assert!(matches!(
            &events[2],
            StreamEvent::Usage(usage)
                if usage["total_tokens"] == json!(18)
                    && usage["prompt_tokens_details"]["cached_tokens"] == json!(8)
        ));
```

两点核验：

1. **键位已按 r5 修法改正**。`usage["prompt_tokens_details"]["cached_tokens"]`
   对透传的原始对象取嵌套值得 `8`，与 `json!(8)` 相等（serde_json 非负
   整数同为 PosInt 表示，相等成立）。
2. **修正在提交内，不是工作区悬空态**。`git show 4b784bb4` 中该测试
   新增即为嵌套键形状（夹具行与断言行都是 `prompt_tokens_details`），
   即 r5 #6 的翻案在父代理合入前已被采纳；`git status` 无 providers/mod.rs
   未提交改动。台账 R5-6 的「验证轮首跑前必须修」事项**就此关闭**。

顺带全量重推该测试的事件流（静态）：块 1（content "early" +
finish_reason:"stop"）→ 1 事件、置位不发 Done；块 2（迟到 content
" late"，宽松网关面）→ 1 事件、`openai_choices_finished` 为 false
不改写标志位（只在 true 时 store，`:307-310`）；块 3（`choices:[]` +
usage）→ 空数组按 `:338` 判 false，仅出 Usage 事件；`[DONE]` → 清标志
（`:200-201`）+ Done。合计 4 事件、序恰为 content/content/Usage/Done，
`finish_stream()` 因 `swap(false)`（`:318-320`）已被 `[DONE]` 清空而返回
空——`assert_eq!(events.len(), 4)` 与末行断言全部成立。**静态判绿**。

## 二、修正后的键位钉住的是真实生产契约（本轮新增证据）

r5 只证了「顶层键不存在所以断言挂」；本轮补证反向命题——**嵌套形状
正是下游消费的形状**，修正后的断言不是迁就实现的随手改，而是钉住契约：

- Chat 适配器不走 `build_usage_event` 归一化（该函数仅 Responses
  `:2251/:2253` 与 Anthropic `:2716` 调用，r5 已 grep 核实无旁路），
  `StreamEvent::Usage` 携带原始对象；
- 生产消费点 1：`model2_pipeline.rs` 捕获 usage（`:5585-5587`）后经
  `extract_usage_tokens`（`:8049`）记账，缓存命中按
  `prompt_tokens_details.cached_tokens` 读取（`:8112-8115`），与
  Anthropic/Responses/DeepSeek/Gemini 形状取 max 防中转站重复；
- 生产消费点 2：`chat_v2/pipeline/llm_adapter.rs:101-104` 同样按嵌套
  形状读取（`:91` 注释明示 OpenAI Chat Completions 即此形状）。

即：Chat 面「透传原始形状、下游各自归一化」的分层是既定设计，
`build_usage_event` 归一化出的顶层 `cached_tokens` 属于 Responses/
Anthropic 面。测试按嵌套形状断言，与两条下游路径一致。**确认**。

## 三、include_usage 终止状态机：产品代码复核，无回归

自 55846040 落地以来该段零改动（r5 亦未触碰），本轮独立重走一遍：

- **choice 完成 ≠ 流完成**：`finish_reason` 仅经
  `openai_choices_finished`（`:329-344`）置位 `saw_finish_reason`
  （`:307-310`）；空 `choices` 恒 false，多 choice 要求全部带非空
  finish_reason，部分完成不算。置位后遇到后续未完成块**不回落**
  （只在 true 时 store）——语义正确：网关补发迟到内容后直接断连，
  EOF 仍应按已见 finish_reason 收口。
- **Done 三来源**互斥完备：`[DONE]`（`:199-204`，同时清标志）、流内
  `{"error":...}` 注入（`:209-221`，清标志 + SafetyBlocked + Done）、
  EOF `finish_stream()`（`:317-326`，`swap(false)` 一次性消费防重复）。
- **本轮补核 1——官方 `usage: null` 噪声面**：官方端点开启 include_usage
  后，除末尾 usage-only 块外**每个内容块都带 `"usage": null`**。
  `:300` 用 `as_object()` 取值，null 得 None 不出事件——不会为每个
  内容块伪造 Usage 事件。此面此前任何轮次未记录，现记为已核安全。
- **本轮补核 2——标志位跨流污染面**：`build_request` 开头重置标志
  （`:153-154`）提供复用兜底；生产实例化点全部为按次新建
  （`model2_pipeline.rs:7012-7021` 循环体内每模型新建、
  `llm_manager/mod.rs:3258` 工厂、`commands.rs:1875`、
  `streaming_harness.rs:53`），无共享实例并发消费两条流的现行调用面。
  r1 提的「trait 文档注明单流所有权」仍未做，维持遗留（§六）。
- **pipeline EOF 接线**：`upstream_ended` 时 `finish_stream()` 推入
  `parsed_blocks` **尾部**（`model2_pipeline.rs:5377-5383`，行号自 r1
  记录的 `:5011` 漂移至此，逻辑未变），保证尾随 usage 块先入队；
  严格终止门 `require_terminal_success`（`:4884`）+ 缺失终止判失败
  （`:5797-5806`）+ `validate_stream_termination`（`:5814-5824`）与
  Done 事件置 `terminal_success`（`:5660-5662`）、`[DONE]` 裸行后备
  （`:5387-5403`）的闭环完整。省略 `[DONE]` 的网关经 EOF 的
  finish_stream 出 Done → 终止门满足，不误判截断。

## 四、stream_options 门控：产品代码复核，无回归

- 注入条件三与（`:161-172`）：`stream == true`（JSON 布尔，字符串
  `"true"` 等异形不注入，fail-safe）&&
  `is_official_openai_api_endpoint(base_url)` && 调用方未显式设置
  `stream_options`（含显式 `false` 与显式 `null` 均尊重原值不覆盖）。
- 门控函数（`:130-135`）：trim + `url::Url` 解析 + host 小写后精确等于
  `api.openai.com`。解析失败（无 scheme / 空串）fail-safe 不注入。
  端口变体（如 `:8443`）host 仍相等会注入——official host 自带端口
  属罕见但无害形态，不构成缺陷。
- **本轮补核——sanitize 与注入的次序交互**：`sanitize_openai_request_body`
  （`:614-651`）只处理 `tools` / `tool_choice`，不读不删
  `stream_options`；注入在 sanitize 之后对 sanitized 对象操作，
  调用方显式值经 sanitize 原样存活后再被 `contains_key` 尊重。
  次序正确，无「sanitize 吞掉显式值导致误注入」的暗面。
