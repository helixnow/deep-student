# R1-WI-10：内置 Skill 组 Token 预算基准（SA-R1-09）

> 分支：`cursor/optimization0824-5575`
> 日期：2026-08-24
> 子代理：SA-R1-09（模型 `claude-fable-5-thinking-xhigh`）
> 测试：`tests/vitest/chat-v2/token-budget.test.ts`

## 目标

为渐进披露架构下每个 builtin skill 组（`src/features/chat/skills/builtin-tools/`）
的 `embeddedTools` schema 建立可回归的 token 预算基线，识别最冗长的组，
防止 schema 无节制膨胀吞掉上下文窗口。

## 测量口径

- **schema**：`JSON.stringify(skill.embeddedTools)` 的字符数 —— 即技能激活后注入
  LLM 请求的工具定义体积。
- **content**：`skill.content` 的字符数 —— 即技能激活后注入 system prompt 的指令文本。
- **token 估算**：`chars / 4`（向上取整）。`@dqbd/tiktoken` 不在 npm 依赖中
  （精确计数走 Rust 侧 `tiktoken-rs` 的 `estimate_tokens` Tauri 命令，vitest
  环境不可用），为保证测试离线、确定性、零新增依赖采用该经典近似。
  **注意**：schema/content 中大量中文描述的实际 token 密度更高（≈1 token/汉字），
  chars/4 是「下界」；实际消耗预计为估算值的 1.5–2.5 倍。作为组间相对排序与
  回归护栏，该口径足够稳定。
- 技能收集绕过 `filterBuiltinToolSkillsForPlatform` 的平台过滤，覆盖全部 43 组
  （含 jsdom 下会被滤掉的 `browser-tools`）。

## 观察与后续建议（供 WI-10 R2 收口参考）

1. `qbank-tools` 30 个工具 / 7.4k tokens（下界），是第二名的 1.56 倍。建议 R2
   评估按使用频率拆分为核心组 + 扩展组，或压缩重复的参数描述。
2. `workspace-tools`（22 工具）与 `session-manager`（20 工具）工具数量偏多，
   存在按场景二次分组的空间。
3. `textbook-pdf-tools` 仅 3 个工具却有 1.8k tokens schema（平均 599 tokens/工具，
   全库平均 192），单工具描述极重，是精简描述文本的首选目标。
4. `mindmap-tools`、`workspace-tools` 的 content（指令文本）都超过 1.7k tokens，
   schema 之外的 system prompt 注入也值得关注。
