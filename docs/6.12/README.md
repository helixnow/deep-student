每个子代理启动后必须先读本文件,再读自己的 `agent-{N}.md`,然后开始工作。

## 2. 工作目标(每个代理相同)

1. **全面深入审阅**:通读职责域内全部代码,识别 bug、坏味道、性能隐患、安全风险、
   交互/体验问题、不一致的约定。
2. **优化**:在职责域内实施低风险、可验证的改进;高风险改动先在状态文档中登记方案,
   等用户确认。
3. **持续记录**:全程维护自己的状态文档(见第 4 节),保证任何时刻中断后,
   新会话都能凭文档无缝接力。

## 3. 全局规则(必须遵守)

### 3.1 职责边界
- 只修改自己 `agent-{N}.md` 列出的职责域内文件。
- 发现职责域外的问题:**不要直接改**,记录到自己状态文档的「跨组问题」一节,
  注明涉及文件、问题描述、建议归属的代理编号。

### 3.2 共享文件(高冲突风险,特别约定)
以下文件被多组共同触碰,只允许修改与自己域直接相关的段落,并在状态文档中登记改动范围:

| 文件 | 说明 | 一致性负责人 |
|------|------|--------------|
| `src-tauri/src/commands.rs` (~196KB) | Tauri 命令实现集合 | 代理 7 |
| `src-tauri/src/lib.rs` (~127KB) | 命令注册与应用装配 | 代理 7 |
| `src-tauri/src/models.rs` (~71KB) | 共享数据模型 | 代理 2 |
| `src/App.tsx` (~103KB) | 前端主框架 | 代理 7 |
| `src/main.tsx` | 入口装配 | 代理 7 |
| `src/locales/**`(i18n 文案) | 各组可增改自己域的 key,不改别组 | 代理 7 |

### 3.3 改动纪律
- 小步修改,每完成一个内聚的改动就跑一次验证(见 3.4),保持仓库随时可构建。
- 禁止大规模重命名/移动文件、禁止引入新依赖、禁止改构建配置,除非用户明确同意。
- **未经用户明确要求,不执行 git commit / push**;保持工作区改动可被用户审查。
- 不删除、不重写其他代理的状态文档。

### 3.4 验证命令
前端(任何 `src/` 改动后):

```bash
npm run typecheck      # TypeScript 类型检查
npm run lint           # ESLint
npm test               # Vitest 单测(可用 -- <pattern> 缩小范围)
```

后端(任何 `src-tauri/` 改动后,在 `src-tauri/` 目录执行):

```bash
cargo check
cargo clippy -- -D warnings   # 以现状为基线,不引入新警告
cargo test <模块名>            # 职责域相关测试
```

i18n 文案改动后:`npm run check:i18n`。

## 4. 状态文档规范(每个代理必须维护)

- 路径:`docs/6.12/status/agent-{N}-status.md`(不存在则由代理自己创建;
  已存在则**先通读再接力**,禁止清空重写)。
- 更新频率:每完成一个审阅单元/一次改动/一次重要发现,立即更新。
- 必含章节(模板):

```markdown
# 代理 {N} 状态文档 —— {代号}

## 任务目标
(从 agent-{N}.md 摘要,首次启动时填写)

## 当前状态
(一句话:正在做什么 / 阻塞在哪)最后更新:YYYY-MM-DD HH:mm

## TODO 计划
- [ ] 待办(按优先级排列,完成打勾并标注日期)

## 审阅发现
| # | 文件/位置 | 类型(bug/性能/安全/体验/坏味道) | 严重度(高/中/低) | 描述 | 处理(已修复/待修复/建议) |

## 已实施的优化
| # | 改动文件 | 改动说明 | 验证结果(typecheck/lint/test) |

## 跨组问题(发现但不属于本组职责域)
| # | 涉及文件 | 问题描述 | 建议归属代理 |

## 共享文件改动登记
| # | 文件 | 改动段落/函数 | 原因 |

## 接力须知
(若本会话中断,新会话继续前必须知道的上下文)
```

## 5. 跨组接口(先冻结再并行)

| 接口 | 上游 | 下游 | 约定 |
|------|------|------|------|
| OCR 产物 → 向量化入库 | 代理 3 | 代理 2 | 解析输出结构变更需双方在状态文档登记并同步 |
| 试卷切题调用 OCR | 代理 4 | 代理 3 | 代理 4 只消费,不改 OCR 内部实现 |
| Pipeline 调用 LLM/技能/MCP/记忆 | 代理 1(域内自洽) | — | 合并后域内自管 |
| 题目 → 制卡 | 代理 5 | 代理 4 | 题目数据结构以代理 4 为准 |
| 全局 UI 组件/design tokens | 各组 | 代理 7 | 各组不改 `components/ui` 基础件,问题报给代理 7 |
| 移动端适配层 | 代理 8 | 各 UI 组 | 见 agent-8.md 的「修改权限分级」 |

## 6. 建议执行顺序

并行启动没有硬性障碍,但若分批,建议:
1. **第一批**:代理 2(数据层)、代理 7(平台基座)——它们的结论影响面最大;
2. **第二批**:代理 1(对话引擎)、代理 3(文档解析);
3. **第三批**:代理 4、5、6(业务层)、代理 8(移动端,可全程穿插)。
